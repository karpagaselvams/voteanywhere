1. Project Overview and Objectives

1.1 Project Title

Vote Anywhere: Remote Polling System Simulator for Geographically Mobile Voters

1.2 Introduction and Background

In democratic elections, voters may find themselves geographically distant from their registered polling centre due to work, education, or other commitments. Vote Anywhere simulates a workflow that allows such voters to request and receive approval to vote at alternative polling centres without compromising their eligibility or changing their registered constituency.

The system demonstrates modern web application architecture, security best practices, and the critical concepts involved in secure electoral systems. It incorporates voter authentication, role-based authorization, ballot secrecy principles, encryption, audit trails, and state management.

1.3 Project Objectives

  • Simulate a complete remote polling workflow for geographically mobile voters
  • Implement secure voter authentication using mock OTP mechanisms with rate limiting
  • Enforce role-based authorization for five distinct officer and voter roles
  • Maintain ballot secrecy by completely separating voter identity from candidate choices
  • Provide AES-256-GCM encrypted ballot storage with integrity verification
  • Prevent duplicate ballot submissions using database constraints within transactions
  • Generate comprehensive audit trails for all state-changing operations
  • Simulate post-election ballot counting and constituency-level reconciliation
  • Demonstrate secure password handling, session management, and JWT token use
  • Provide separate user portals for voters, officers, and system administrators

1.4 Scope and Academic Boundaries

Features Included:

  • Full remote polling request and approval workflow
  • Voter authentication, registration, and eligibility verification
  • Officer and administrator access with role-based control
  • Constituency-based ballot generation and encryption
  • Election simulation, counting, and reconciliation
  • Comprehensive audit logging and access control
  • Session management with password change and logout

Academic Project Boundary:

This is a workflow simulator using fictional data. It does not connect to or claim capabilities for:

  • Real Election Commission of India (ECI) systems or data
  • Actual electoral rolls, voter databases, or Aadhaar integration
  • Real SMS/Email OTP services or biometric authentication
  • Distributed consensus, quorum, or multi-node election networks
  • Production-grade cryptographic infrastructure or HSM integration
  • Real elections or actual voter participation

Data Note: All voters, constituencies, polling centres, candidates, and elections used in this system are entirely fictional and generated for demonstration purposes only.

2. Domain Concepts and Terminology

2.1 Core Entities

Voter

A fictional person holding a record in the system's voter register. Each voter has a unique voter ID, registration details, and a registered constituency that determines their ballot.

Registered Constituency

The constituency where a voter is officially enrolled. This is permanently assigned and determines the candidates presented on their ballot. It is never changed by remote polling approval.

Polling Centre

A physical location where voting takes place. Each polling centre belongs to exactly one constituency. Elections are conducted simultaneously across all polling centres in a constituency.

Remote Polling Centre

An alternative polling centre, typically in a different constituency, that a voter requests to use because they are geographically distant from their registered constituency during an election.

Remote Polling Request

A voter's formal application to vote at a remote polling centre for a specific election. These are reviewed, approved, or rejected by Verification Officers based on eligibility criteria.

Remote Polling Assignment

The approved authorization resulting from an accepted request. It grants a specific voter permission to appear at a named remote polling centre for a named election.

2.2 The Fundamental Core Rule

A remote polling centre changes WHERE a voter votes. It never changes the voter's registered constituency or the ballot they receive.

Example Scenario:

AttributeValue
VoterArjun (Voter ID: V12345)
Registered ConstituencyChennai South
Current LocationMadurai (away during election)
Requested Remote CentreMadurai Constituency Centre
Approved Location to VoteMadurai Centre
Ballot ConstituencyChennai South (unchanged)

Arjun will vote at the Madurai polling centre, but receives the Chennai South ballot with Chennai South candidates.

2.3 Ballot Secrecy Principle

The system is architected around the fundamental principle that voter identity must never appear alongside candidate choice in any API response, log entry, database view, or audit record.

  • Opaque References: Submitted ballots are referred to only by random, non-sequential ballot references that carry no voter information
  • Data Separation: Voter records and candidate choice data are maintained in separate database schemas and never joined in API responses
  • Encryption: Candidate choices are stored only in encrypted form (AES-256-GCM)
  • Audit Safety: Audit records never contain decrypted candidate choices, only ballot actions and references
  • Logging: Application logs never pair voter identity with candidate selection

4. User Roles and Permissions

4.1 The Five Roles

Vote Anywhere implements five distinct roles with precisely defined permissions. Role enforcement occurs in backend middleware, not in frontend UI hiding.

1. Voter

Responsibilities:

  • Authenticate using mock OTP
  • View personal eligibility information
  • Submit remote polling requests
  • View request status and approval decisions
  • Access and submit ballots for assigned elections
  • Change personal password

Cannot: Access officer functions, view other voters' data, approve requests, or configure elections

2. Verification Officer

Responsibilities:

  • Review voter eligibility information
  • Review remote polling requests submitted by voters
  • Approve or reject remote polling requests
  • Provide rejection reason when applicable
  • View voter records and eligibility status

Cannot: Access ballots, configure elections, manage users, or modify voter records

3. Polling Centre Officer

Responsibilities:

  • Verify voters at polling centre
  • Manage polling centre operations for assigned centre
  • View assigned polling centre information
  • Support voter verification using remote polling assignments

Cannot: Approve requests, access ballots, configure elections, or manage other centres

4. Election Administrator

Responsibilities:

  • Create and configure elections
  • Manage constituencies and candidates
  • Activate and close elections
  • Manage polling centres
  • Create and manage officer accounts

Cannot: Access ballots, approve requests, or modify audit records

5. System Auditor

Responsibilities:

  • Review audit trail records
  • View all state-changing operations
  • Verify ballot integrity and reconciliation reports
  • Access historical logs and decisions

Cannot: Modify any data, approve requests, or access decrypted ballots

5. Core Modules and Functionality

5.1 Authentication Module

Voter Authentication (OTP-based)

  • Mock OTP Generation: Creates fictional 6-digit OTP for voters
  • OTP Validation: Single-use, time-limited (15 minutes expiry)
  • Rate Limiting: Maximum 3 incorrect attempts per 15 minutes
  • Session Creation: JWT token issued on successful OTP verification
  • Password Setup: Voters set password during first OTP login
  • Password Change: Self-service password change with current password verification

Officer Authentication (Password-based)

  • Username + Password Login: Standard credentials-based authentication
  • Password Security: Minimum 8 characters, bcrypt with 10 salt rounds
  • Session Management: JWT token with role-based claims
  • Password Change: Requires current password verification, revokes all other active sessions
  • Account Lockout: After 5 failed attempts in 30 minutes (subject to configuration)

5.2 Voter Management Module

  • Voter Registration: Create fictional voter records with unique IDs
  • Eligibility Verification: Check voter status, age, and constituency registration
  • Constituency Assignment: Link voters to registered constituencies permanently
  • Duplicate Prevention: Prevent duplicate voter entries via database constraints
  • Profile Management: Allow voters to view and update personal information
  • Record Search: Officers can search voter records for eligibility checks

5.3 Election Management Module

Election Lifecycle

  • Creation: Administrators create elections with name, date, and scope
  • Configuration: Define constituencies, candidates, and voting rules
  • Activation: Transition election to active state and enable voting
  • Closure: End voting period and prevent new submissions
  • Archival: Preserve historical election data for audit

Candidate Management

  • Create candidates with names, party affiliations, and constituency assignments
  • Assign candidates to constituencies within elections
  • Prevent invalid candidate configurations (e.g., one candidate per constituency)
  • Support fictional data for demonstration

5.4 Remote Polling Workflow Module

Request Submission

  • Voter submits request specifying desired remote polling centre
  • Request linked to specific election and voter
  • Submission timestamp recorded in audit trail
  • Initial status: "PENDING_REVIEW"

Officer Review and Approval

  • Verification Officer reviews pending requests
  • Officer verifies voter eligibility (active status, not previously voted in election)
  • Officer reviews requested polling centre validity
  • Officer makes approval or rejection decision with optional reason
  • Decision recorded in audit trail with timestamp and officer ID

Request States

PENDING_REVIEW → APPROVED → ASSIGNED (terminal) ↓ (rejected) REJECTED (terminal) ↓ (cancelled) CANCELLED (terminal)

Assignment Creation

  • Upon approval, automatic assignment created
  • Assignment specifies voter, election, and remote polling centre
  • Polling Centre Officer uses assignment to verify voter at centre
  • Assignment is location-specific and election-specific

5.5 Ballot Module

Ballot Generation

  • Generate ballot from voter's registered constituency, not remote centre
  • Ballot contains candidates from registered constituency for the election
  • Ballot generation triggered when voter accesses voting interface
  • Unique ballot reference (opaque, non-sequential) assigned

Ballot Encryption and Storage

  • Encryption Algorithm: AES-256-GCM (authenticated encryption)
  • Key Management: Master encryption key stored securely in environment
  • Storage: Encrypted candidate choice stored separately from voter data
  • Integrity: GCM mode provides authentication tag for tampering detection

Ballot Submission and Duplicate Prevention

  • Voter submits encrypted candidate choice with ballot reference
  • Duplicate Prevention: Database unique constraint on (voter_id, election_id)
  • Constraint Enforcement: Within transaction to prevent race conditions
  • Error Handling: Graceful rejection if voter already submitted for election
  • Audit Recording: Submission recorded without revealing voter-choice pair

6. Database Design and Schema

6.1 Core Tables

User and Authentication Tables

  • officers: Officer accounts with username, hashed password, role
  • sessions: Active officer sessions with JWT tokens and expiry
  • voters: Voter records with ID, name, age, registered constituency
  • voter_sessions: Voter session records with OTP and authentication state

Electoral Data Tables

  • constituencies: Constituency records with unique identifiers
  • polling_centres: Polling location data linked to constituencies
  • elections: Election configuration with status and date
  • candidates: Candidate records linked to elections and constituencies

Ballot and Voting Tables

  • ballots: Generated ballots with constituency, opaque references
  • ballot_submissions: Submitted ballots with encrypted choices (no voter-choice pair)
  • ballot_encryption_metadata: IV and salt for decryption (never the key)

Remote Polling Tables

  • remote_polling_requests: Voter requests with status and reasons
  • remote_polling_assignments: Approved assignments linking voter to remote centre

Audit and Compliance Tables

  • audit_log: Immutable audit records of state-changing operations
  • integrity_verifications: Records of ballot integrity checks performed

6.2 Key Design Principles

Ballot Secrecy Through Schema Design

  • Voter data (voters, voter_sessions) in one schema
  • Ballot data (ballots, ballot_submissions) in separate schema
  • No foreign key joining voters to candidate choices
  • Opaque ballot references prevent voter identification

Duplicate Submission Prevention

UNIQUE (voter_id, election_id) ON ballot_submissions Enforced within database transaction Prevents race condition even with concurrent submissions

Audit Trail Immutability

  • Audit records append-only (no updates or deletes)
  • Timestamp and actor recorded for every operation
  • Never contains plaintext passwords, OTPs, or decrypted choices
  • Operations referenced by their IDs, not by data contents

7. Security Implementation

7.1 Authentication Security

Password Security

  • Hashing: bcrypt with 10 salt rounds (modern standard)
  • Minimum Requirements: 8 characters minimum (enforced client and server)
  • Never Logged: Passwords never appear in logs or audit records
  • Transmission: HTTPS-only (TLS 1.2+) in production

OTP Security

  • Generation: Cryptographically random 6-digit codes
  • Lifetime: 15-minute expiry from generation
  • Single Use: OTP invalidated after successful verification
  • Rate Limiting: Maximum 3 attempts per 15-minute window
  • Storage: Hashed in database (not plaintext)

Session Management

  • JWT Tokens: Signed with HMAC-SHA256, includes role claims
  • Token Expiry: Role-specific expiration (6-24 hours)
  • Server-side Sessions: Token validated against database session record
  • Logout: Session invalidated immediately, user must re-authenticate
  • Password Change: Revokes all other active sessions of that user

7.2 Ballot Integrity and Encryption

Encryption Scheme

  • Algorithm: AES-256-GCM (256-bit key, authenticated encryption)
  • IV (Initialization Vector): 96-bit random value per encryption
  • Authentication Tag: 128-bit GCM tag ensures no tampering
  • Plaintext: Candidate choice encrypted and stored

Integrity Verification

  • GCM authentication tag checked during decryption
  • Tampering detection if ciphertext is modified
  • Audit trail records integrity verification attempts
  • Decrypted choice never persisted or logged

8. Authorization and Role-Based Access Control

8.1 Authorization Architecture

Enforcement Layer

  • Middleware-Based: Every backend endpoint protected by authorization middleware
  • Role Checking: Request validated against endpoint's allowed roles
  • Whitelist Model: Deny all by default, allow only explicitly permitted roles
  • Token Validation: JWT token verified and role extracted from claims

Permission Enforcement

Authorization Middleware Flow: 1. Extract JWT token from Authorization header 2. Verify token signature and expiry 3. Retrieve user and role from token claims 4. Check if role is in endpoint's allowed_roles list 5. Grant access if authorized, return 403 Forbidden otherwise 6. Record authorization check in audit log

8.2 Frontend UI Cannot Be Used for Authorization

Frontend hiding of buttons or pages is NOT a security measure. Authorization is enforced at the backend API level:

  • If a voter manually navigates to an officer endpoint URL, the backend rejects the request
  • Hidden UI elements provide user experience only, not access control
  • Every single API endpoint validates the caller's authorization
  • Frontend may optimize UX by hiding irrelevant controls, but backend is the true gatekeeper

9. Audit Trail and Compliance

9.1 Audit Trail Design

What Gets Recorded

Every state-changing operation is recorded:

  • Voter login (successful and failed attempts)
  • Officer login (successful and failed attempts)
  • Remote polling request submission
  • Remote polling approval or rejection decisions
  • Ballot generation
  • Ballot submission (with opaque reference, not candidate choice)
  • Election creation, activation, closure
  • Officer or voter account creation/modification
  • Password changes and session revocation
  • Authorization failures (unauthorized access attempts)
  • Ballot integrity verification results

What Never Gets Recorded

  • Plaintext passwords or OTP codes
  • JWT token values
  • Encryption keys or decrypted candidate choices
  • Voter identity alongside candidate choice (ballot secrecy)
  • Database credentials or connection strings

9.2 Audit Record Structure

Each audit record contains: - audit_id: Unique identifier - timestamp: When the operation occurred (UTC) - actor_id: Who performed the action (user/officer/system) - actor_role: Role of the actor - operation: Type of operation (LOGIN, SUBMIT_REQUEST, etc.) - resource_id: ID of affected resource - resource_type: Type of resource (VOTER, BALLOT, etc.) - status: Success/failure status - details: Operation-specific details (never contains secrets)

9.3 Audit Trail Access

  • System Auditor Role: Can read full audit trail
  • Officer Roles: Can read audit records relevant to their operations
  • Voters: Can read their own audit records only
  • Audit Access Itself Audited: Audit trail reads are recorded in the audit trail

13. Known Limitations and Future Work

13.1 Current Limitations

By Design (Academic Scope)

  • Mock OTP only—no real SMS/Email integration
  • Fictional voter data only—no real electoral roll connection
  • Single-instance simulator—not a distributed system
  • In-memory OTP cache—does not persist across server restarts
  • No biometric authentication
  • No multi-factor authentication (MFA) for officers
  • Simplified password policy (may be enhanced for production)

Technical Constraints

  • No horizontal scaling of ballot encryption (key management simplified)
  • No blockchain or distributed ledger (by design—single authority)
  • Limited offline functionality (web-based only)
  • No native mobile applications
  • Database-level rate limiting not implemented (application-level only)

13.2 Potential Future Enhancements

  • Integration with mock ECI API for realistic electoral data
  • SMS/Email OTP delivery through third-party services
  • Biometric voter verification (fingerprint/iris simulation)
  • Multi-factor authentication (TOTP-based) for officers
  • End-to-end encryption for communications
  • Blockchain-based ballot verification (for demonstration)
  • Mobile-responsive native applications
  • Enhanced audit report generation and analytics
  • Disaster recovery and failover procedures
  • International language support (beyond English and regional languages)

14. Conclusion

Vote Anywhere successfully demonstrates a complete remote polling workflow system with modern security practices, role-based access control, and comprehensive audit trails. The project showcases full-stack web development capabilities using contemporary technologies and architectural patterns.

The system prioritizes ballot secrecy, data protection, and compliance through:

  • Careful schema design separating voter and ballot data
  • Encryption of candidate choices with authenticated encryption (AES-256-GCM)
  • Backend-enforced authorization on every endpoint
  • Comprehensive immutable audit trails
  • Duplicate submission prevention via database constraints
  • Secure password and OTP handling

While constrained as an academic project using fictional data, Vote Anywhere demonstrates core principles applicable to real electoral systems and serves as a foundation for further development and enhancement.
