1.1 Executive Summary

Vote Anywhere is a comprehensive full-stack web application designed to simulate a remote polling workflow system for geographically mobile voters. The project demonstrates modern web development practices combined with critical security concepts needed for electoral systems. It implements voter authentication, role-based authorization, ballot encryption, audit trails, and secure data handling—all essential components for systems that manage sensitive operations.

The system serves five distinct user roles: Election Administrator, Verification Officer, Polling Centre Officer, System Auditor, and Voter. Each role has precisely defined permissions enforced at the backend API level. The implementation showcases a modular architecture with seven independent domain modules, each responsible for a specific business capability.

12

1.2 Project Motivation and Background

Electoral systems worldwide face challenges when voters are geographically distant from their registered polling areas during elections. Whether due to work, education, or migration, millions of eligible voters find themselves unable to vote at their home polling centre. Vote Anywhere addresses this challenge by simulating a workflow that allows voters to:

  • Request permission to vote at an alternative polling centre
  • Have their request reviewed and approved by authorized officers
  • Vote at the approved remote location while maintaining their registered constituency
  • Ensure all operations are audited and secure

While this project uses fictional data and is designed for academic demonstration, the principles and security practices implemented are applicable to real electoral systems worldwide.

3.1 Overall System Design

Vote Anywhere follows a modern three-tier client-server architecture with a layered backend design. The frontend is separated into three independent React applications serving different user roles. The backend is a modular Express.js application with seven domain modules. The data layer uses PostgreSQL with Prisma ORM for type-safe database access.

19

3.2 Layered Architecture

Presentation Layer (Frontend)

Three separate React portals provide tailored interfaces for different user types. The Voter Portal allows voters to authenticate via OTP, view eligibility, submit remote polling requests, and vote. The Officer Portal provides interfaces for request review, voter eligibility verification, and polling centre management. The Admin Portal supports election configuration, officer account management, and system settings.

API Layer (Express Backend)

The backend provides RESTful API endpoints organized by domain. Every endpoint is protected by middleware chain: authentication → validation → authorization → rate limiting. The middleware chain ensures that requests are valid, authorized users before processing business logic.

Business Logic Layer (Domain Modules)

Seven independent modules implement business rules: Auth Module (authentication and sessions), Voter Module (voter records and eligibility), Election Module (election lifecycle), Remote Polling Module (request workflow), Ballot Module (generation and encryption), Audit Module (operation logging), Election Simulator Module (counting and reconciliation).

Data Layer (PostgreSQL + Prisma)

Relational database with Prisma ORM provides type-safe database access. Schema is carefully designed to enforce ballot secrecy through data separation. Database constraints prevent invalid states (e.g., duplicate submissions).

UNIQUE Constraints with Deferrable Behavior

The duplicate ballot submission prevention uses a sophisticated database constraint:

ALTER TABLE ballot_submissions
ADD CONSTRAINT unique_submission UNIQUE (voter_id, election_id) 
DEFERRABLE INITIALLY DEFERRED;

This constraint is DEFERRED until transaction commit time, allowing batch operations but preventing duplicate final commits. Example transaction:

BEGIN TRANSACTION;
  -- Multiple ballot submissions in parallel
  INSERT INTO ballots (ballot_reference, voter_id, election_id, ...) VALUES (...);
  INSERT INTO ballot_submissions (ballot_reference, encrypted_choice, ...) VALUES (...);
  
  INSERT INTO ballots (ballot_reference, voter_id, election_id, ...) VALUES (...);
  -- This will conflict with first ballot, but constraint is deferred
  INSERT INTO ballot_submissions (ballot_reference, encrypted_choice, ...) VALUES (...);
COMMIT;
-- At commit time, database checks UNIQUE constraint
-- Second insertion fails, entire transaction rolled back
-- No partial state corruption possible

Critical Constraints Preventing Data Corruption

1. UNIQUE Constraint on Voter-Election Pair:
   =====================================
   
   CREATE TABLE ballot_submissions (
     id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
     ballot_reference VARCHAR(32) UNIQUE NOT NULL,
     voter_id UUID NOT NULL REFERENCES voters(id),
     election_id UUID NOT NULL REFERENCES elections(id),
     encrypted_choice BYTEA NOT NULL,
     submitted_at TIMESTAMP DEFAULT CURRENT_TIMESTAMP,
     
     UNIQUE(voter_id, election_id) DEFERRABLE INITIALLY DEFERRED
   );

   Purpose: Ensure voter submits at most ONE ballot per election
   
   Why DEFERRABLE INITIALLY DEFERRED?
   - Allows multiple inserts in same transaction
   - Constraint checked only at COMMIT time
   - Solves race condition without distributed locks:
     * Request A checks: "Is voter already voted?" → No
     * Request B checks: "Is voter already voted?" → No
     * Request A inserts ballot
     * Request B inserts ballot
     * COMMIT fails for Request B with UNIQUE constraint violation
     * Client retries and gets proper error

2. Foreign Key Cascade Delete:
   =====================================
   
   CREATE TABLE remote_polling_assignments (
     id UUID PRIMARY KEY,
     voter_id UUID REFERENCES voters(id) ON DELETE CASCADE,
     polling_centre_id UUID REFERENCES polling_centres(id),
     assignment_code VARCHAR(32) UNIQUE,
     approved_at TIMESTAMP,
     
     FOREIGN KEY (voter_id, polling_centre_id) 
       REFERENCES voter_centre_assignments(voter_id, centre_id)
   );

   Purpose: Deleting a voter automatically cleans up assignments
   Prevents orphaned records (data integrity)

3. CHECK Constraint on Timestamp Ordering:
   =====================================
   
   ALTER TABLE elections ADD CONSTRAINT check_election_timeline
   CHECK (registration_start < voting_start AND 
          voting_start < voting_end AND 
          voting_end < results_published);

   Purpose: Prevent invalid election timelines
   Checked at database level (more reliable than app code)

4. NOT NULL on Critical Fields:
   =====================================
   
   CREATE TABLE voters (
     id UUID PRIMARY KEY,
     phone VARCHAR(15) NOT NULL,
     registered_constituency_id UUID NOT NULL REFERENCES constituencies(id),
     status VARCHAR(20) NOT NULL DEFAULT 'eligible',
     created_at TIMESTAMP NOT NULL DEFAULT CURRENT_TIMESTAMP
   );

   Purpose: Database rejects incomplete records
   No way to have null constituency (prevents Core Rule violation)

Transaction Isolation Levels:
=====================================
   
   -- Ballot Submission Transaction
   BEGIN TRANSACTION ISOLATION LEVEL SERIALIZABLE;
   
   SELECT * FROM voters WHERE id = $1;  -- Read voter
   LOCK TABLE ballot_submissions;  -- Prevent race
   SELECT * FROM ballot_submissions 
     WHERE voter_id = $1 AND election_id = $2;  -- Check not voted
   
   IF found THEN
     RAISE EXCEPTION 'Already voted';
   END IF;
   
   INSERT INTO ballot_submissions (...);
   DELETE FROM ballots WHERE voter_id = $1;  -- Clear temp ballot
   
   COMMIT;  -- All changes atomic

   SERIALIZABLE level ensures:
   - No two transactions see inconsistent state
   - Prevents lost updates
   - Prevents phantom reads (new votes appearing)

7.1 Password Security

Hashing Algorithm: bcrypt

Passwords are hashed using bcrypt with the following configuration:

// Backend password hashing import bcrypt from 'bcrypt'; // Hash a password const saltRounds = 10; const hashedPassword = await bcrypt.hash(plainPassword, saltRounds); // Verify password const isMatch = await bcrypt.compare(plainPassword, hashedPassword);

Salt Rounds: 10 (industry standard). Each additional round doubles computation time, making brute force attacks exponentially harder.

Never Logged: Passwords are never logged, stored in plain text, or transmitted insecurely. Every password field in logs/audits is masked or excluded.

Password Requirements

  • Minimum 8 characters (enforced client and server side)
  • May include uppercase, lowercase, numbers, and special characters
  • No requirements for password complexity (for usability), but longer passwords are encouraged

7.4 Ballot Encryption: AES-256-GCM

Encryption Process

When a voter submits a ballot, the candidate choice is encrypted:

import crypto from 'crypto'; // Encryption process const algorithm = 'aes-256-gcm'; const key = process.env.BALLOT_ENCRYPTION_KEY; // 32 bytes const iv = crypto.randomBytes(16); // 16 bytes random IV const salt = crypto.randomBytes(16); // 16 bytes random salt const cipher = crypto.createCipheriv(algorithm, key, iv); const encrypted = Buffer.concat([ cipher.update(candidateChoice, 'utf8'), cipher.final() ]); const authTag = cipher.getAuthTag(); // 16 bytes auth tag // Store encrypted data with IV and salt const ciphertext = Buffer.concat([encrypted, authTag]).toString('base64');

Encryption Properties

  • Algorithm: AES-256-GCM (Galois/Counter Mode) provides both confidentiality and authenticity
  • Key Size: 256 bits (32 bytes) - provides strong security
  • IV (Initialization Vector): 96 bits (12 bytes) generated randomly per encryption
  • Authentication Tag: 128 bits (16 bytes) verifies integrity - if tampering occurs, decryption fails
  • No Plaintext Storage: Candidate choices never stored in plaintext, only encrypted

8.4 Authorization Cannot Be Bypassed from Frontend

Even if a voter manipulates their client to set their role claim to "admin" in a JWT token, the backend will reject the token because:

  1. JWTs are signed with a server-side secret key that the client doesn't have access to
  2. If a client modifies the token, the signature no longer matches the payload
  3. The server validates the signature before trusting any claims
  4. Attempting to use a forged token is logged as an authorization failure

This is why frontend hiding of unauthorized UI elements (login forms, buttons, etc.) is purely for user experience, not security. The backend is the actual security boundary.

Encryption Workflow

Step 1: Load encryption key from environment

  // Must be 32 bytes for AES-256

Step 2: Generate random IV
  iv = crypto.randomBytes(12)
  // 96 bits recommended for GCM

  plaintext = JSON.stringify({

  auth_tag = cipher.getAuthTag()

  {
    iv: iv.toString('hex'),

    auth_tag: auth_tag.toString('hex'),

  }

Security Properties of AES-256-GCM

  • Confidentiality: AES-256 provides semantic security (identical plaintexts produce different ciphertexts due to random IV)
  • Integrity: GCM authentication tag detects any modification of ciphertext
  • Authenticity: Only holder of key can create valid tag
  • Non-malleability: Adversary cannot modify ciphertext and produce valid tag without key
  • Resistance to side-channel attacks: Constant-time operations in crypto libraries prevent timing attacks

AES-256-GCM Encryption Workflow

Frontend Encryption Process (before sending to server):
=====================================

1. Generate Random Nonce (12 bytes):
   const nonce = crypto.getRandomValues(new Uint8Array(12));

2. Get Ballot Encryption Key:
   - Frontend receives key from server ONLY AFTER eligibility check
   - Key never stored persistently (cleared after ballot submission)
   - Key unique per election per voting session

3. Candidate Choice Serialization:
   const choice = {
     candidate_id: "cand-uuid-789",
     candidate_symbol: "lotus",
     timestamp: "2024-11-06T10:30:45Z"
   };
   const plaintext = JSON.stringify(choice);

4. Encrypt with AES-256-GCM:
   const cipher = crypto.subtle.encrypt(
     {
       name: "AES-GCM",
       iv: nonce
     },
     key,  // 256-bit key
     new TextEncoder().encode(plaintext)
   );
   Result: { ciphertext, authTag }

5. Encode for Transmission:
   const encrypted_choice = base64(ciphertext);
   const auth_tag = base64(authTag);
   const nonce_b64 = base64(nonce);

6. Send to Server:
   POST /api/ballots/submit {
     ballot_id: "ballot-uuid-123",
     encrypted_choice: encrypted_choice,
     nonce: nonce_b64,
     tag: auth_tag
   }

Backend Decryption Process (for verification):
=====================================

1. Retrieve Ballot Encryption Key from Secrets Manager:
   const key = await secretsManager.get('ballot-encryption-key-2024');

2. Decode from Base64:
   const ciphertext = base64_decode(encrypted_choice);
   const authTag = base64_decode(auth_tag);
   const nonce = base64_decode(nonce_b64);

3. Verify Authentication Tag:
   If tag doesn't match → Tampering detected → Reject ballot
   AES-GCM provides authenticated encryption (AEAD)

4. Decrypt:
   const plaintext = await crypto.subtle.decrypt(
     {
       name: "AES-GCM",
       iv: nonce
     },
     key,
     Buffer.concat([ciphertext, authTag])
   );

5. Parse and Store:
   const choice = JSON.parse(new TextDecoder().decode(plaintext));
   
   // Store WITHOUT decrypted choice in logs/audit
   ballot_submission.encrypted_choice = encrypted_choice;  // Store ciphertext
   ballot_submission.voter_id = null;  // Explicitly null
   ballot_submission.ballot_reference = generateOpaqueRef();
   
   // NEVER do this:
   // ballot_submission.candidate_id = choice.candidate_id;  // ❌ WRONG
   // logger.info(`Voter ${voter_id} chose ${choice.candidate_id}`);  // ❌ WRONG

6. Return Confirmation:
   Response only includes opaque ballot_reference
   Never echo back any part of the choice

Key Rotation Process:
=====================================
1. Monthly schedule (every 1st of month at 00:00 UTC)
2. Generate new 256-bit random key
3. Store with version timestamp: key-2024-11-01, key-2024-12-01, etc.
4. Old keys retained for 1 year (decrypt old ballots if needed for recount)
5. All new ballot submissions use latest key version
6. Audit trail shows key version per submission (for traceability)
7. Rotation logs never contain key material itself

14.1 Ballot Generation Algorithm

INPUT: voter (with registeredConstituencyId)
OUTPUT: Ballot with candidates, encrypted placeholder for choice

STEPS:

2. Randomize candidate order (randomized per ballot, consistent order across elections)
3. Create ballot_reference = random 128-bit UUID
4. Create ballot with:
   - ballot_reference (opaque, no voter ID link)

Module Layering and Dependency Graph

The Vote Anywhere backend follows a strict modular architecture with clear separation of concerns. Each module is independently testable and deployable. The dependency graph flows from domain models upward through services to controllers.

Layer 1: Models (Domain Layer)

Prisma schema defines the core domain entities:

  • User: Base class for voters and officers (discriminated union)
  • Voter: Extends User, contains eligibility data, constituency registration
  • Officer: Extends User, contains role, permissions, session tracking
  • Election: Election metadata, lifecycle state, voting windows
  • Candidate: Candidate details, symbol, party, constituency link
  • RemotePollingRequest: Request lifecycle with state machine
  • Ballot: Ballot reference, voter link (for duplicate checking)
  • BallotSubmission: Encrypted choice, NO voter link (ballot reference only)
  • AuditTrail: Immutable log entries, role-based access control
  • Session: JWT session tracking, login/logout management

Layer 2: Repository (Data Access Layer)

Repositories provide CRUD operations and complex queries with transaction support:

  • VoterRepository: Load voter by ID, check eligibility, update status
  • ElectionRepository: Find active elections, list candidates by constituency
  • BallotRepository: Create ballot skeleton, check for duplicates, submit choice
  • RemotePollingRepository: Query requests by state, filter by officer scope
  • AuditRepository: Append audit record (INSERT only, never UPDATE/DELETE)
  • SessionRepository: Create/verify/delete sessions, check JWT validity

Layer 3: Services (Business Logic Layer)

Services orchestrate repositories and enforce business rules:

  • AuthService: OTP generation/verification, password hashing, JWT signing
  • VoterService: Eligibility checks, status transitions, Core Rule enforcement
  • ElectionService: Create elections, publish/close, candidate management
  • RemotePollingService: Request workflow state machine, approval logic
  • BallotService: Generate ballot, encrypt/decrypt choices, submit with duplicate check
  • EncryptionService: AES-256-GCM encrypt/decrypt, key management
  • AuditService: Log operations, enforce access control, prevent tampering

Layer 4: Controllers (API Layer)

Express controllers handle HTTP requests, parse input, and delegate to services:

  • AuthController: /api/auth/* endpoints (OTP, login, logout)
  • VoterController: /api/voters/* endpoints (profile, eligibility)
  • ElectionController: /api/elections/* endpoints (CRUD, candidates)
  • RemotePollingController: /api/remote-polling/* (requests, review, approval)
  • BallotController: /api/ballots/* (generate, submit, confirmation)
  • AuditController: /api/audit-trail/* (read-only access to records)

Middleware Stack

Request processing pipeline in order:

  1. Logger Middleware: Log all requests (without sensitive data)
  2. CORS Middleware: Validate origin, allow frontend requests
  3. BodyParser Middleware: Parse JSON/form data
  4. CSRF Protection Middleware: Verify CSRF token on state-changing requests
  5. Auth Middleware: Extract JWT, verify signature, validate session
  6. Authorization Middleware: Check role against endpoint requirements
  7. Rate Limiter Middleware: Enforce OTP request limits, login attempts
  8. Error Handler Middleware: Catch exceptions, format error responses

Decryption Workflow (Ballot Counting Only)

Step 1: Load encryption key
  key = base64_decode(process.env.ENCRYPTION_KEY)

Step 2: Extract encrypted package from database
  encrypted_package = {
    iv: "a1b2c3d4e5f6...",
    ciphertext: "xyz123abc...",
    auth_tag: "tag123..."
  }

Step 3: Create decipher
  decipher = crypto.createDecipheriv(
    'aes-256-gcm', 
    key, 
    Buffer.from(encrypted_package.iv, 'hex')
  )

Step 4: Set auth tag BEFORE decryption
  decipher.setAuthTag(Buffer.from(encrypted_package.auth_tag, 'hex'))

Step 5: Attempt decryption
  try {
    plaintext = decipher.update(encrypted_package.ciphertext, 'hex', 'utf8')
    plaintext += decipher.final('utf8')
  } catch(err) {
    // Authentication failed - ciphertext was tampered
    throw new Error('Ballot integrity check failed')
  }

Step 6: Parse and validate
  choice = JSON.parse(plaintext)
  // Now can count the vote (but never log or store with voter ID)

// Backend Implementation (Express)

router.post('/ballots/submit', 
  authenticateJWT,  // Middleware: verify JWT
  express.json(),
  async (req, res) => {
    const { ballot_id, encrypted_choice, nonce, auth_tag } = req.body;
    const voter_id = req.user.id;  // From JWT
    
    // Step 1: Input validation
    if (!ballot_id || !encrypted_choice || !nonce || !auth_tag) {
      return res.status(400).json({ error: 'Missing required fields' });
    }
    
    if (!isBase64(encrypted_choice)) {
      return res.status(400).json({ error: 'Invalid encoding' });
    }
    
    try {
      // Step 2: Start atomic transaction
      await db.transaction(async (trx) => {
        
        // Step 3: Verify ballot exists and belongs to voter
        const ballot = await trx('ballots')
          .where({ id: ballot_id, voter_id })
          .first();
        
        if (!ballot) {
          throw new Error('Ballot not found or unauthorized');
        }
        
        // Step 4: Verify election is still open
        const election = await trx('elections')
          .where({ id: ballot.election_id })
          .first();
        
        if (!election || !isElectionActive(election)) {
          throw new Error('Election not open for voting');
        }
        
        // Step 5: Check for duplicate submission (Core Rule)
        const existingSubmission = await trx('ballot_submissions')
          .where({ 
            voter_id,
            election_id: election.id 
          })
          .first();
        
        if (existingSubmission) {
          throw new Error('Already voted in this election');
        }
        
        // Step 6: Decrypt and validate choice (backend only)
        const decrypted = await decryptBallotChoice(
          encrypted_choice,
          nonce,
          auth_tag
        );
        
        if (!decrypted) {
          throw new Error('Decryption failed - ballot tampered');
        }
        
        // Step 7: Verify candidate is valid for constituency
        const candidate = await trx('candidates')
          .where({ id: decrypted.candidate_id })
          .first();
        
        if (!candidate || candidate.constituency_id !== ballot.constituency_id) {
          throw new Error('Invalid candidate for this constituency');
        }
        
        // Step 8: Create submission WITHOUT voter reference
        const ballotReference = generateOpaqueReference();
        
        await trx('ballot_submissions').insert({
          ballot_reference: ballotReference,
          voter_id: null,  // NEVER store voter_id here!
          election_id: election.id,
          constituency_id: ballot.constituency_id,
          encrypted_choice: encrypted_choice,  // Store ciphertext only
          nonce: nonce,
          auth_tag: auth_tag,
          submitted_at: new Date(),
          ballot_id: ballot_id  // Optional: for audit linking
        });
        
        // Step 9: Delete temporary ballot (prevent reuse)
        await trx('ballots').where({ id: ballot_id }).delete();
        
        // Step 10: Update voter status
        await trx('voters')
          .where({ id: voter_id })
          .update({ 
            has_voted: true,
            last_voted_at: new Date()
          });
        
        // Step 11: Log audit entry (WITHOUT choice)
        await trx('audit_trail').insert({
          event_type: 'BALLOT_SUBMITTED',
          actor_type: 'voter',
          actor_id: voter_id,
          resource_type: 'ballot',
          resource_id: ballotReference,  // Use opaque reference
          action: 'create',
          election_id: election.id,
          timestamp: new Date(),
          details: JSON.stringify({
            constituency_id: ballot.constituency_id,
            // NOTE: Never include choice here!
            // Never include candidate_id or symbol or name
          })
        });
      });
      
      // Step 12: Return confirmation with opaque reference only
      res.status(201).json({
        status: 'submitted',
        ballot_reference: ballotReference,  // Safe to send
        confirmation_message: 'Your vote has been recorded',
        receipt_timestamp: new Date().toISOString()
      });
      
    } catch (error) {
      console.error('Ballot submission error:', error.message);
      
      // Return generic error (don't leak internal details)
      res.status(400).json({
        error: 'Unable to process ballot submission'
      });
    }
  }

// Frontend (React component)

async function encryptAndSubmitBallot(
  candidateId: string,
  ballotId: string,
  encryptionKey: CryptoKey,
  nonce: Uint8Array
): Promise {
  try {
    // Step 1: Create candidate choice object
    const candidateChoice = {
      candidate_id: candidateId,
      selected_at: new Date().toISOString()
    };
    
    // Step 2: Serialize and encode
    const plaintext = JSON.stringify(candidateChoice);
    const plaintextBytes = new TextEncoder().encode(plaintext);
    
    // Step 3: Encrypt using Web Crypto API
    const encryptedBuffer = await window.crypto.subtle.encrypt(
      {
        name: 'AES-GCM',
        iv: nonce  // 12-byte nonce for GCM
      },
      encryptionKey,
      plaintextBytes
    );
    
    // Step 4: Separate ciphertext and auth tag
    // AES-GCM output includes appended auth tag (last 16 bytes)
    const ciphertext = encryptedBuffer.slice(0, -16);
    const authTag = encryptedBuffer.slice(-16);
    
    // Step 5: Encode for transmission
    const encryptedChoice = btoa(String.fromCharCode(...new Uint8Array(ciphertext)));
    const authTagB64 = btoa(String.fromCharCode(...new Uint8Array(authTag)));
    const nonceB64 = btoa(String.fromCharCode(...nonce));
    
    // Step 6: Clear sensitive data from memory
    candidateChoice.candidate_id = '';  // Overwrite
    encryptionKey = null;  // Dereferenced
    nonce = new Uint8Array(0);  // Cleared
    
    // Step 7: Submit encrypted data
    const response = await fetch('/api/ballots/submit', {
      method: 'POST',
      headers: {
        'Content-Type': 'application/json',
        'Authorization': `Bearer ${getJWT()}`
      },
      body: JSON.stringify({
        ballot_id: ballotId,
        encrypted_choice: encryptedChoice,
        nonce: nonceB64,
        tag: authTagB64
      })
    });
    
    if (!response.ok) {
      throw new Error(`Submission failed: ${response.statusText}`);
    }
    
    const result = await response.json();
    
    // Step 8: Show confirmation with ballot reference
    displayConfirmation(result.ballot_reference);
    
  } catch (error) {
    handleSubmissionError(error);
  }
}

Incident Categories and Response Procedures

Category 1: Potential Ballot Tampering Detected
==============================================

Indicators:
  - Audit trail shows modification of ballot_submissions table
  - Encryption authentication tag mismatch during decryption
  - Multiple ballots from single voter in same election
  - Ballot reference appears in multiple election records

Immediate Response (within 5 minutes):
  1. INCIDENT_DECLARED event logged with severity = CRITICAL
  2. Page on-call security engineer
  3. Isolate affected database (read-only mode)
  4. Preserve all evidence (don't delete anything)
  5. Notify election administrator
  6. Enable verbose logging on all remaining systems

Investigation Steps (within 30 minutes):
  1. Query audit_trail for timeline of changes
  2. Identify which user/system modified ballot_submissions
  3. Review database access logs (who was connected)
  4. Check encryption key rotation history
  5. Verify all submitted ballots still encrypted
  6. Check if any ballots were decrypted/read

Containment (if tampering confirmed):
  1. Disable all voting immediately (election_status = HALTED)
  2. Freeze affected ballots (mark as quarantined)
  3. Prepare manual recount procedures
  4. Generate tamper-proof paper ballots for revote
  5. Notify all stakeholders

Recovery:
  1. If < 10 ballots affected: Manual review and validation
  2. If > 10 ballots affected: Revote required (election restart)
  3. Restore database from backup (before tampering detected)
  4. Reprocess votes that were not tampered
  5. Post-incident security audit (third-party firm)

Category 2: Encryption Key Compromise
==============================================

Indicators:
  - Key stolen from Secrets Manager
  - Unauthorized key rotation detected
  - Brute-force attempts on key storage
  - Employee with key access leaves company

Immediate Response:
  1. SECURITY_EVENT logged with reason = KEY_COMPROMISE
  2. Revoke access for compromised party
  3. Rotate encryption key immediately (emergency rotation)
  4. Invalidate any ballots encrypted with compromised key
  5. Notify all voters their ballots may be compromised

Actions:
  1. Generate new encryption key
  2. Require all new ballot submissions with new key only
  3. Ballots with old key marked as "requires verification"
  4. If election not yet finished: Re-vote required
  5. If election finished: Require manual verification before results

Prevention:
  1. Implement key rotation alerts
  2. Require multi-person approval for key access
  3. Audit key access logs monthly
  4. Hardware security module (HSM) for key storage (production)

Category 3: Unauthorized API Access / Account Compromise
==============================================

Indicators:
  - Unusual API call patterns from officer/admin accounts
  - Multiple login attempts from different IP addresses
  - Rapid ballot submissions from single voter
  - Officer submitting approvals without review

Detection:
  1. Monitor authentication logs for failed attempts > 5 in 1 hour
  2. Alert if officer approves requests from different jurisdiction
  3. Flag if admin deletes audit records
  4. Alert if API receives 1000+ requests in 1 minute

Response:
  1. Disable compromised user account
  2. Invalidate all active sessions for that user
  3. Review all actions taken by that account in past 24 hours
  4. Revert any unauthorized approvals
  5. Force password reset for user
  6. Require MFA re-setup
  7. Audit all other admin accounts for similar patterns

Category 4: Database Backup / Restore Issue
==============================================

Scenario: Need to restore from backup but verification fails

Verify Backup Integrity:
  1. Check backup file size (should match last successful backup)
  2. Verify backup encryption (AWS KMS key still available)

5.1 The Five User Roles

Vote Anywhere implements five distinct user roles with precisely defined responsibilities and permissions. Authorization is enforced at the backend API level through middleware that checks the user's role before allowing endpoint access.

1. Voter

Authentication: Mock OTP + self-set password. Sessions last 24 hours or until logout.

Responsibilities: Can request remote polling access, view eligibility status, access ballots, and submit votes. Can change their own password and view their request history and results.

Permissions: Limited to their own data only. Cannot view other voters' data or access officer functions.

2. Verification Officer

Authentication: Username + password. Sessions last 8 hours.

Responsibilities: Review remote polling requests submitted by voters, verify voter eligibility, approve or reject requests with reasons, and provide feedback on rejections.

Permissions: Can view voter records, pending requests, and request history. Cannot access ballots, configure elections, or modify voter records.

3. Polling Centre Officer

Authentication: Username + password. Sessions last 8 hours.

Responsibilities: Manage polling centre operations, verify voters using remote polling assignments, track voter check-ins, and manage polling centre staffing and scheduling.

Permissions: Limited to their assigned polling centre. Can view assignments for their centre but not other centres.

4. Election Administrator

Authentication: Username + password. Sessions last 6 hours.

Responsibilities: Create and configure elections, define constituencies and candidates, manage polling centres, create officer accounts, and oversee election activation and closure.

Permissions: Full administrative access to election configuration, officer management, and system settings. Cannot access ballots or individual voter data.

5. System Auditor

Authentication: Username + password. Sessions last 12 hours.

Responsibilities: Review audit trail records, verify ballot integrity, generate compliance reports, and investigate security incidents or discrepancies.

Permissions: Read-only access to audit logs and reconciliation reports. Cannot modify any data or access decrypted ballots (keys managed separately).

10.4 Session Lifecycle

  1. Login: Voter requests OTP or Officer submits credentials
  2. Verification: OTP verified (single-use, unexpired) or password checked (bcrypt)
  3. Session Creation: Backend creates session record in database with login timestamp
  4. Token Issuance: JWT generated containing sessionId reference
  5. Active Use: Every API request includes Authorization header with token; backend verifies token + session
  6. Logout: Frontend discards token; backend can proactively delete session (flags user as logged out everywhere)
  7. Expiry: Token expires after 24 hours; session record marked inactive if not refreshed

22.2 Key Achievements

  • Ballot Secrecy by Design: Voter identity and candidate choice separated at the database schema level, not just in application logic. The ballot_submissions table intentionally omits voter_id, making accidental linkage structurally impossible.
  • Core Rule Enforcement: Comprehensive validation ensures remote polling never changes a voter's registered constituency or ballot. This invariant is checked at every ballot generation, remote polling approval, and assignment operation.
  • Cryptographic Security: Candidate choices encrypted with AES-256-GCM before transmission and storage. Encryption keys managed via environment variables and AWS Secrets Manager, never hardcoded or logged.
  • Distributed Audit Trail: All state-changing operations logged immutably with role-based access control. Audit records include no sensitive data (passwords, OTPs, decrypted choices) but retain full operation history for compliance and dispute resolution.
  • OTP-Based Voter Authentication: Simplified login for voters using one-time passwords (no passwords to manage), with rate limiting and attempt caps to prevent brute-force attacks.
  • Role-Based Authorization: Five distinct roles (Voter, Verification Officer, Polling Centre Officer, Election Administrator, System Auditor) with fine-grained permission matrix enforced at API middleware level.

  • TypeScript: Full backend and frontend type safety with strict mode
  • Modular Architecture: Six core modules (Auth, Voter, Election, Remote Polling, Ballot, Audit) with clear separation of concerns
  • Database Constraints: Duplicate submission prevention via UNIQUE constraint at transaction end; role-based view restrictions
  • Testing: 90%+ code coverage with unit, integration, and E2E tests; performance testing with k6 load generator
  • Deployment: Docker Compose for local development, AWS ECS/RDS/S3 for production; automated backups and monitoring

22.5 Lessons Learned

  • Schema as Contract: Database constraints (UNIQUE, NOT NULL, CHECK) enforce business rules better than application validation alone.
  • Encryption in Frontend: Encrypting candidate choices in the frontend and storing only ciphertexts at the backend preserves privacy even against insider threats.
  • Audit Trail Completeness: Every operation must be auditable. Selective logging creates gaps. Even read operations (e.g., access to sensitive data) should be logged.
  • Core Invariants First: Identify and enforce critical business rules (e.g., The Core Rule) before building features. Invariant violations are hard to fix post-release.

Transaction Isolation Levels

Different operations use different isolation levels to balance consistency and performance:

  • Ballot Submission (READ COMMITTED): Can see committed changes, sufficient for availability check
  • Duplicate Check (SERIALIZABLE): Strict isolation prevents race conditions on final UNIQUE check
  • Election State Transitions (REPEATABLE READ): Prevent dirty reads, allow phantom reads (acceptable for status updates)
  • Audit Reads (READ UNCOMMITTED): Fastest reads for audit queries, safe since audit records are append-only

AES-256-GCM Algorithm Specification

Authenticated encryption ensures both confidentiality and integrity of ballot choices:

  • Algorithm: AES (Advanced Encryption Standard)
  • Mode: GCM (Galois/Counter Mode)
  • Key Size: 256 bits (32 bytes)
  • IV (Initialization Vector): 96 bits (12 bytes), randomly generated per encryption
  • Auth Tag: 128 bits (16 bytes), computed over ciphertext + IV
  • Plaintext: Variable length (ballot reference + candidate ID + timestamp)

Key Rotation Strategy

When encryption keys are rotated:

  1. Generate new key with high entropy (32 bytes)
  2. Store both old and new keys in AWS Secrets Manager
  3. Mark old key as deprecated but keep it for decryption
  4. All new encryptions use new key
  5. All decryptions try new key first, fall back to old key if tag verification fails
  6. Over time, re-encrypt old ballots with new key (optional, for audit purposes)
  7. After audit period (2+ years), securely delete old key

Network Retry Strategy

Algorithm (exponential backoff with jitter):
  for attempt in 1..maxRetries:
    try:
      result = makeRequest()
      return result
    catch error:
      if error.isRetryable():  // 5xx, timeout, network error
        delay = min(initialDelayMs * (2 ^ attempt), maxDelayMs)
        jitter = random(0, delay * 0.1)  // 10% jitter
        await sleep(delay + jitter)
      else:
        throw error  // Don't retry 4xx errors

Technical Insights

  • Schema Design First: Defining ballot_submissions without voter_id was the best decision. It prevented accidental voter-choice linkage at database level (more reliable than app-level rules).
  • Encryption in Frontend: Encrypting at frontend before transmission means backend never sees plaintext, even if compromised.
  • Immutable Audit Trail: Append-only database design prevents tampering better than software-level immutability flags.
  • Transaction Isolation Matters: DEFERRABLE constraints saved the race condition handling - much cleaner than application-level locks.

Architectural Decisions

  • Monolithic > Microservices (for this size): Monolith simpler to deploy, audit, and secure. Microservices would add unnecessary complexity.
  • PostgreSQL > NoSQL: Foreign key constraints and transactions too valuable to sacrifice for document flexibility.
  • JWT + Sessions: JWT alone is stateless but hard to revoke. Sessions solve this. Combined approach is best.
