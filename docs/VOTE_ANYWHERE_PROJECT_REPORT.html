ABSTRACT


Elections are fundamental to democratic processes, but the geographic mobility of voters poses a persistent and practical challenge to electoral participation. A citizen who has moved to another city for work, study or medical treatment, and who is therefore away from the constituency in which they are registered, frequently cannot travel back to vote. The distance may be a few hundred kilometres or a few thousand; the effect is the same. The voter remains eligible, remains enrolled, and yet is effectively excluded from the poll. This project addresses that problem as an academic exercise in workflow simulation.

Vote Anywhere: A Remote Polling System Simulator for Geographically Mobile Voters is a BCA final-year project that models the complete administrative journey of a geographically mobile voter. The system begins with voter authentication, proceeds through eligibility verification and the submission of a remote polling request, routes that request to a Verification Officer for claim, review, approval or rejection, generates an approved remote polling assignment, and finally presents a controlled ballot and records the submitted choice. At every state change the system writes an audit record describing the actor, the timestamp and the operation.

The design is organised around one invariant, referred to throughout the report as the Core Rule: a remote polling centre changes where a voter votes; it never changes the voter’s registered constituency or the ballot they receive. The rule is not merely documented. It is enforced by the shape of the data model — the approved remote polling assignment carries no constituency column at all — and by the signature of the ballot-generation service, which accepts an entire voter record rather than a loose constituency identifier, making it impossible for a caller to pass the remote centre’s constituency by accident.

A second invariant, ballot secrecy, is enforced structurally. The database contains two disjoint tables: an identity-side table that records only that a voter voted, and a choice-side table that records only what was chosen. No foreign key, shared key or Prisma relation connects them. The candidate choice is sealed with AES-256-GCM under a key read from a single module and validated at first use, with the ballot reference, election identifier and constituency identifier bound into the associated data so that a stored ciphertext cannot be relocated to another row. Verification of a stored ballot is a decryption attempt that returns only a boolean; a separate function opens a ballot for counting and is reachable only from the Election Simulator after an election has closed.

v

The application implements five roles — Election Administrator, Verification Officer, Polling Centre Officer, System Auditor and Voter — with authorization enforced by explicit allow-list middleware on the server rather than by hiding pages in the browser. Officers authenticate with a bcrypt-hashed password and a JSON Web Token backed by a revocable server-side session record; voters authenticate with a mock one-time password delivered through a development-only channel. Neither path reveals whether an account exists, because both run a bcrypt comparison against a dummy hash on the failure path and return an identical status and body.

The implementation comprises a React 19 and TypeScript single-page frontend built with Vite and styled with Tailwind CSS 4, a Node.js and Express 4 backend written in TypeScript and organised into nine domain modules, and a PostgreSQL 16 database whose structure is defined by Prisma 6 and created by versioned SQL migrations. Duplicate ballot submission is rejected by a unique database constraint rather than by an application-level check, so two simultaneous submissions cannot both succeed. A partial unique index, hand-written in the migration because Prisma cannot express it, permits at most one active remote polling request per voter per election.

All voter records, constituencies, polling centres, candidates and election data are fictional and are produced by an idempotent seed script. The system does not connect to a real electoral roll, a government service or a biometric system, and it does not conduct an actual election. It is a workflow simulator whose value lies in the visibility of its invariants: a reviewer can confirm the Core Rule and the ballot-secrecy boundary by reading the Prisma schema alone, without running the application.

The report documents the analysis, design, implementation and testing of this system across eight chapters, supported by forty-one figures, thirty-eight tables, twenty-nine numbered code sketches and an appendix containing the full data dictionary, the REST reference, the traceability matrix and the complete test log.

CHAPTER 1
INTRODUCTION

1.1 Overview of the Project

Vote Anywhere is a web-based simulation of a remote polling workflow for geographically mobile voters. It is a full-stack application developed as a final-year BCA project, and its purpose is to demonstrate, in working software, how an electoral administration could allow an eligible voter who is away from their registered constituency to vote at an authorised alternative polling centre — while preserving the two properties that make such a scheme defensible: that the voter receives the ballot of the constituency in which they are actually enrolled, and that nobody, including the operators of the system, can learn how any individual voted.

The system models five roles. A Voter authenticates with a mock one-time password, checks their eligibility, submits a remote polling request naming an alternative polling centre and a reason, and later casts a controlled ballot. A Verification Officer claims requests from a queue, reviews them, and approves or rejects them with a recorded reason. A Polling Centre Officer performs pre-vote verification at a centre, confirming that an arriving voter holds a valid assignment. An Election Administrator configures elections, activates and closes them, and reads aggregate reports. A System Auditor reads the audit trail and the post-closure reconciliation report in read-only mode. Every one of these interactions is a real HTTP request against a real database; none of them is a mock-up in the interface.

The application is organised as a modular monolith: a single Express service, internally divided into nine domain modules, sitting behind a single-page React frontend, with PostgreSQL 16 beneath it. The choice of a monolith over microservices is deliberate and is discussed in Section 4.2. The system needs to be comprehensible to an examiner and maintainable by one developer; a service mesh would add operational surface without adding a single enforceable invariant.

What distinguishes this project from a generic election CRUD application is that its central claims are enforced by construction rather than by convention. The claim that a remote polling centre does not change a voter’s constituency is enforced by the absence of any constituency field on the assignment record and by the type signature of the ballot service. The claim that a vote cannot be linked to a voter is enforced by the absence of any join between the two tables that would be needed to make that link. The claim that a voter cannot vote twice is enforced by a unique database constraint that holds even if two requests arrive in the same millisecond. These are design decisions, and the report treats them as the substance of the project.

Academic disclaimer. All voters, constituencies, polling centres, candidates, officer accounts and election data are fictional and are generated by a seed script. The application does not connect to the electoral roll of any country, to the Election Commission of India, to Aadhaar, to any biometric service or to any government API, and it does not conduct an election. It is a workflow simulator for academic assessment.

1.1.1 What the Application Actually Does

It is worth stating the workflow plainly before the surrounding analysis. A voter opens the application and selects the Voter tab on the sign-in screen. They enter their voter number, receive a six-digit one-time code through the development channel, and exchange it for a session token. On the dashboard they see their registered constituency, their home polling centre, the current election and its lifecycle state, and their own latest request with its status. They may then run an eligibility check, which reports four separate conditions and whether each passed.

If the election is still in the CONFIGURED state, the voter may submit a remote polling request. They choose a polling centre from a list; each entry is labelled with the constituency that centre belongs to. The service refuses a centre that lies inside the voter’s own registered constituency, because voting at one’s home centre is not remote polling and needs no permission. It also refuses a second active request, and this refusal is enforced by a partial unique index rather than by a read-then-write check in application code.

On the officer side, a Verification Officer sees a review queue filtered by status. Claiming a request moves it from PENDING to UNDER_REVIEW and records the reviewer. Approving it creates a RemotePollingAssignment in the same database transaction; an approved request with no assignment would leave a voter at a centre with nothing to verify against, so the two writes either both land or neither does. Rejecting it requires a non-empty reason, which is stored and shown to the voter.

Once the administrator activates the election, the ballot becomes available. The controlled ballot page lists the candidates standing in the voter’s registered constituency — not the remote centre’s — and, if the voter holds an assignment, displays the remote centre as a location. Submitting a choice seals it under AES-256-GCM, writes both sides of the secrecy boundary inside one transaction, and returns only an opaque ballot reference. A second submission is refused by the database.

After the administrator closes the election, two read-only reports become available. The reconciliation report compares, per constituency, the number of ballots issued against the number recorded and reports any discrepancy as a discrepancy rather than attempting to resolve it by matching individuals — because that match is precisely what ballot secrecy forbids. The results report decrypts each ballot inside the Election Simulator and produces aggregate counts per candidate per constituency.

1.2 Background of the Study

Every large democracy has a structural tension between the locality of representation and the mobility of the population it represents. Parliamentary and assembly constituencies are defined geographically. A voter is enrolled in the constituency where they are ordinarily resident, and that enrolment determines which candidates appear on their ballot. Because the ballot is a contest between candidates standing in a particular constituency, it follows that a voter cannot simply be handed a different constituency’s ballot on the day of the poll without changing the composition of the electorate that elects that constituency’s representative.

At the same time, internal migration is large. In India, the Census of India has consistently recorded a very substantial volume of intra-state and inter-state movement driven by employment, marriage, education and family circumstance. A large share of this movement is circular rather than permanent: a worker may spend most of the year in a city while retaining a family home and an enrolment in a distant district. The COVID-19 period made the scale of this population visible in a way that earlier statistics had not.

The consequence for electoral administration is a group of voters who are legally entitled to vote, who are correctly enrolled, and who are physically unable to reach their assigned polling station within the polling window. Electoral commissions have responded with a family of measures: postal ballots for specified categories such as service voters and electors on election duty, proxy voting in some jurisdictions, extended polling hours, and, in a small number of countries, arrangements for voting at any polling station within a defined area.

The last of these — remote or out-of-constituency voting — is the most general and the most difficult. It is difficult not because transporting a ballot to another location is technically hard, but because the moment a ballot is cast away from the constituency it belongs to, three problems appear at once. First, the ballot must still be the correct ballot: the candidates on it must be those of the voter’s registered constituency, or the election result is corrupted. Second, the secrecy of the ballot must survive the journey: at a remote centre, an official who knows the voter’s identity is standing next to the ballot, so any design that stores an identifiable ballot undermines the secret ballot. Third, the administration must be able to demonstrate afterwards that the number of ballots issued equals the number recorded, without being able to demonstrate who cast which ballot.

These three problems are the design centre of this project. The application is small — a handful of constituencies and a few hundred lines of domain logic — but the invariants it makes visible are the same ones that make real remote voting hard.

1.2.1 The Indian Electoral Context

India’s electoral machinery is unusually centralised in its standards and unusually distributed in its execution. The Election Commission of India sets the rules and the timetable; the actual poll is run by district administration through lakhs of polling stations, each staffed by a presiding officer and polling officers drawn from other government departments. A voter is assigned to one polling station within their constituency and appears there in person, presents identification, is marked on the electoral roll, and proceeds to the ballot unit.

Three features of this arrangement shape the present design. Verification is physical. The identity check happens at a counter, by a person, against a printed roll. A remote polling scheme therefore cannot be purely digital: it must produce a document, or a record, that an officer at the remote centre can check in person. Vote Anywhere models this with the RemotePollingAssignment, and the Polling Centre Officer’s pre-vote verification screen is the digital analogue of that counter.

The ballot is constituency-specific. In a general election a voter in Chennai South receives a ballot listing the candidates for Chennai South. There is no national list. This is what makes the Core Rule of this project a real constraint rather than a stylistic preference: if a remote polling centre in Madurai were allowed to determine the ballot, a Chennai South voter appearing in Madurai would be handed a Madurai Central ballot and would be voting in an election they are not enrolled in.

The audit trail is paper. Presiding officers complete Form 17A, statutory accounts, and a series of declarations; the paper trail is the evidence base for a challenge. Digitising any part of this requires an equivalent, and that equivalent is the AuditRecord table: append-only, written as a side effect of every state change, never editable through an API.

1.2.2 Why Simulation Rather Than a Real System

A student project cannot integrate with a national electoral roll, cannot obtain identity data, and must not handle real personal information. Three options were available: build a prototype that pretends loudly and breaks under questioning, build a purely paper design, or build a simulator with fictional data whose internal consistency is genuine. The third option was chosen. The consequence is that every claim in this report is about the behaviour of the software under fictional data, and none of it is a claim about electoral law. The benefit is that the invariants can be tested honestly — there are twenty-eight automated tests and each one asserts something that an examiner can reproduce.

1.2.3 Balloting Technology That This Project Does Not Use

Because the words “electronic voting” and “blockchain” appear so often in student projects that they have become nearly meaningless, it is worth being explicit about what this system is not. It is not an electronic voting machine; no ballot is cast through it that counts towards any result other than a simulated aggregate. It does not use a distributed ledger. It does not implement homomorphic tallying, zero-knowledge proofs, mix-nets or verifiable shuffle. It does not use a hardware security module; the encryption key lives in an environment variable and the report says so plainly in Section 8.3.

What it does use is a small number of well-understood primitives applied carefully: bcrypt for password and one-time-code hashing, AES-256-GCM for authenticating a sealed ballot, a cryptographically secure random number generator for every identifier and nonce, and a relational database with real constraints for the invariants that must survive concurrency. The intellectual content of the project lies not in exotic cryptography but in the placement of these primitives: the decision that the secrecy boundary is a schema boundary, and the decision that the Core Rule is enforced by a function signature rather than by a comment.

This restraint is itself an argument. A great many academic proposals for election technology fail not because their cryptography is weak but because their architecture makes an invariant unstateable. If the constituency can be supplied by the caller, no amount of encryption will keep the correct ballot on the correct screen. Vote Anywhere was built from the invariant outwards.

1.3 Problem Statement

The problem addressed by this project can be stated in one sentence:

“There is no lightweight, auditable workflow that lets an enrolled voter who is physically away from their registered constituency vote at an authorised alternative polling centre, while guaranteeing that they receive their own constituency’s ballot, that their choice cannot be linked to their identity, and that the administration can afterwards reconcile the number of ballots issued against the number recorded.”

Each clause of that statement identifies a distinct failure mode in the informal alternatives. The clauses are examined below, and the specific problems that the design must answer are enumerated.

1.3.1 Enumerated Problems

Problem 1 — The ballot-attribution problem. If a voter appears at an alternative centre, whatever system serves them must know which ballot to present. The obvious implementation — take the constituency from the centre the voter is standing in — is wrong, and wrong in a way that silently corrupts results: the voter’s choice would be counted in a constituency where they are not enrolled. The correct source of the constituency is the voter record and nothing else. The design problem is how to make that the only possible source, rather than the intended one.

Problem 2 — The ballot-secrecy problem. A remote voting scheme brings identity and choice into physical proximity. If the database stores a voter identifier beside a candidate choice, then anyone with database access — or anyone who can obtain a report, a log line or an API response — can reconstruct how an individual voted. The design problem is to represent “this voter has voted” and “this choice was made” in a way that no query can join, including queries written by a future maintainer who has never read this report.

Problem 3 — The duplicate-ballot problem. A check of the form “read whether the voter has voted, then write the ballot if not” is incorrect under concurrency. Two requests arriving together can both read “not voted” and both proceed. The design problem is to place the guarantee where it cannot be raced — in the database, not in the service layer.

Problem 4 — The request-lifecycle problem. Approval is not a single flag. A request moves through a defined set of states, and several moves that an implementer might plausibly allow are indefensible: a rejected request must not later be approved without a new application; an approved request must not return to pending; a used request must not be reopened. The design problem is to make every illegal move impossible in one place rather than to scatter conditionals across the code.

Problem 5 — The accountability problem. Every state change must be attributable to an actor and a time, but the audit trail must not itself become a leak. The design problem is to record enough to reconstruct the administration of the poll while recording nothing that reveals a choice or a credential.

1.3.2 Why the Informal Alternatives Fail

Before the software design is considered, it is worth asking why the problem is not already solved by administrative practice. Four informal answers are commonly proposed, and each fails for a specific reason.

Postal balloting. Postal ballots are used in India for defined categories of elector. They work, but they are slow, they require a reliable postal address, and they move the secrecy problem rather than solving it: a postal ballot arrives at a counting centre inside an envelope that bears, at some point in its journey, both an identity and a choice. The covering envelope and the ballot are separated by procedure and by physical handling. Software has no equivalent of “separate the envelope in a locked room” unless the data model is designed to make the separation structural.

Proxy voting. A proxy solution replaces the absent voter with a present one. It solves the travel problem and abandons the personal-vote principle, and it requires a trusted relationship that cannot be verified by a system.

Extended polling windows. Giving the voter more time helps only if the obstacle is time. For a voter two states away, the obstacle is distance, and an extra four hours does not remove it.

Informal local arrangements. The most common practical answer is a phone call and an informal permission. This is precisely what must not happen in an election: it produces no record, no audit, no reconciliation, and no defence if the result is challenged. The existence of informal arrangements is the strongest argument for a formal workflow, because a formal workflow is at least auditable.

1.5.2 Out of Scope

The following are outside the boundary. Where an item is partly present, the limitation is stated precisely rather than glossed.

  • Real identity verification. No Aadhaar, no biometric capture, no electoral-roll lookup, no address proof, no document upload. A voter is identified by a fictional voter number issued by the seed script.

  • Multi-election operation. The service uses the concept of “the current election”. The schema supports many elections and the administrator sees them all, but a voter’s dashboard and the ballot surface resolve a single current election. Concurrent elections for different constituencies are not modelled.
  • Ballot paper fidelity. The ballot lists candidate name and symbol. Party affiliation, symbols as images, NOTA, and multi-seat or preferential voting are absent.
  • Write-side administration. Elections, candidates, polling centres, constituencies and voters are created by the seed script, not by the interface. The administrator activates and closes elections and reads reports but does not create them through the API.
  • Cryptographic end-to-end verifiability. A ballot can be shown to be unmodified, and a reconciliation discrepancy can be reported. The system does not produce a cryptographic proof that the published tally matches the recorded ballots.
  • Distributed deployment. One backend process, one database. No horizontal scaling, no message broker, no cache tier.
  • Full container orchestration. Only PostgreSQL runs in a container at this stage. Development images for the backend and frontend are identified as a later phase in Section 5.5.

1.5.3 Scope Boundary Rationale

Three principles governed where the line was drawn. First, prefer an invariant over a feature. Given limited time, implementing a second report type adds little; implementing the database constraint that makes duplicate ballots impossible adds the thing the project is about. Second, never half-implement a security mechanism. A partial zero-knowledge scheme would be worse than none, because it would invite a claim the code cannot support. Third, keep the fictional boundary visible. Everything that would require real personal data was excluded, so that the system can be demonstrated in a viva without any privacy obligation.

1.6 Project Motivation

The motivation for this project was threefold: a civic observation, an engineering interest, and an academic requirement. They are set out separately because they produced different design decisions.

1.6.1 Civic Motivation

Disenfranchisement by distance is a quiet form of exclusion. It produces no protest because the people affected are, by definition, not in the place where the poll is happening, and it is rarely counted because the denominator — the number of enrolled voters who could not reach their station — is not measured. A student who has moved to Chennai from another district for a three-year degree faces the same choice every election year: travel several hundred kilometres, or do not vote. Many do not vote.

The project does not claim to solve this. A simulator changes nothing about electoral law. But a simulator can make the problem legible, and it can show that the two objections most often raised against remote voting — that it would corrupt the constituency result, and that it would destroy ballot secrecy — are engineering problems with engineering answers, not fatal objections. That, at least, is a contribution a student project can honestly make.

1.6.2 Engineering Motivation

The technical interest lay in a specific class of problem: invariants that must survive other people’s future code. A comment saying “do not pass the remote constituency here” is a wish. A function that cannot accept a constituency at all is a guarantee. Most of the design effort in this project went into converting wishes into guarantees.

Three conversions were particularly instructive. The first was moving duplicate detection from an if statement into a unique index, which required an excursion into partial indexes because the uniqueness only applies to active requests. The second was realising that an approved request and its assignment must be written in one transaction, because an approved request without an assignment is a state in which a voter exists who is permitted to vote remotely but cannot be verified at the centre. The third was separating ballot verification from ballot counting into two functions with different return types, so that the verification path has no type-level way to leak a choice.

The project also exercised a large part of the BCA syllabus in one artefact: relational design and normalisation, SQL constraints and indexes, a typed service layer, HTTP semantics and status codes, client-side routing and form validation, cryptographic hashing, configuration management, containerisation, and systematic testing. The report deliberately documents these connections rather than treating the stack as a list of logos.

1.6.3 Academic Motivation

As a final-year BCA project, the work had to demonstrate proficiency across the programme: database design, software engineering method, web development, and the ability to document a system to a professional standard. The choice of a problem with strong invariants made the engineering method visible. It is easy to write a report about a CRUD application; it is much easier to demonstrate analysis and design when the application has a property that can be violated, and therefore a property that must be argued for, tested, and defended at a viva.

1.7 Assumptions and Constraints

The system is correct only within its assumptions. Stating them is therefore part of stating what the system does.

1.7.1 Assumptions

  1. The voter record is authoritative. The registered constituency stored on the voter record is assumed correct and is never re-derived. No component attempts to infer a constituency from an address, a centre or a location.
  2. Officers are trusted to follow procedure. The system records decisions and reasons but cannot verify that a Verification Officer read the evidence before approving. It can only make the decision attributable.
  3. An approved assignment is honoured physically. The system assumes that a Polling Centre Officer will check the assignment before permitting a ballot. The application supports that check with a verification screen; it cannot compel it.
  4. The clock is monotonic enough. Expiry of sessions and one-time codes uses server time. A grossly incorrect server clock would break expiry without breaking anything else.
  5. A single administrative domain exists. The system assumes one election authority, one electoral roll and one set of constituencies. It does not model federated authorities.
  6. The browser is modern and the network is available. The frontend targets current evergreen browsers and assumes a working connection; there is no offline mode.
  7. Development secrets are adequate for development. The encryption key and JWT secret in .env are development values. The report assumes no adversary with access to the development environment, and says so rather than implying production readiness.
  8. Fictional data is internally consistent. Every voter, centre and candidate is invented, but the relationships between them are real, which is what allows the invariants to be tested.
17

1.7.2 Technical Constraints

  • Single-key ballot encryption. One AES-256 key protects all ballots. Rotating the key makes previously sealed ballots unreadable. This is documented behaviour, not a defect discovered late.
  • Prisma cannot express partial indexes. The constraint that permits at most one active request per voter per election is hand-written SQL inside a migration. It is therefore invisible to Prisma’s schema-diffing and must be maintained by hand.
  • Audit records are not tamper-evident. They are append-only by construction (no update or delete path exists) but are not hash-chained. A party with direct database access could alter them.
  • Counting is in-process. Decryption of every ballot happens in the application. At the scale of a national election this would be untenable; at the scale of a demonstration it is instantaneous.
  • No horizontal scaling. Rate limiting is in-process memory, so a second backend replica would double the effective limit.
  • Tests require a live database. The suites run against a real PostgreSQL 16 instance rather than an in-memory substitute, because the constraints being tested are database features.

1.7.3 Operational Constraints

  • Single developer, single academic term. The project was implemented by one student within one semester, which is why write-side administration of elections and candidates is seed-driven rather than interface-driven.
  • No access to real electoral data. By design and by law, all data is invented.
  • Assessment environment. The demonstration runs on a developer laptop with Docker for PostgreSQL; no cloud infrastructure is assumed.

LITERATURE REVIEW

2.1 Introduction

A project that proposes a workflow for remote polling must first establish that the problem is real, that serious attempts to solve it already exist, and that those attempts leave something worth doing at undergraduate scale. This chapter reviews the literature and the deployed systems in three passes. The first pass examines the systems that governments and electoral commissions have actually operated, because these are the only sources of evidence about what happens when remote voting meets a real electorate. The second pass examines the open research prototypes and the cryptographic literature, because that is where the security arguments live. The third pass examines the technology families that student projects in this area typically adopt — and the reasons several of those families are a trap.

The review is deliberately sceptical. A literature review written for a project that proposes a security-sensitive workflow tends to conclude that every previous system failed and the present one succeeds. That conclusion would be false here. Several deployed systems do considerably more than Vote Anywhere does, with cryptographic guarantees this project does not attempt. The honest conclusion is narrower: the deployed systems are national-scale infrastructure with corresponding complexity, the research prototypes assume cryptographic expertise, and the practical gap is a simple, auditable workflow in which the invariants are visible in the data model — which is exactly the shape a teaching system should take.

2.1.1 Scope and Method of the Review

Sources were selected against four criteria. Relevance: the source must concern out-of-constituency voting, internet voting, or the administration of remote electors. Authority: preference was given to electoral commission publications, peer-reviewed security literature and official standards over vendor marketing. Recency: deployments from the last fifteen years were prioritised, with older foundational work retained where it defines a concept. Verifiability: every claim about a deployed system could be checked against a published report or the operating body’s own documentation.

Fifty-one sources were examined and twenty-four were retained. Sources were excluded where they described a system only in a vendor brochure, where the system had no published operational record, or where the paper proposed a blockchain architecture without an evaluation — a category that, as Section 2.2.6 explains, is large.

2.2 Review of Existing Systems

Six categories of existing work bear on this project. They are reviewed in order of practical significance rather than novelty: the systems that have actually counted votes, then the systems that have been proposed with serious cryptographic backing, then the systems that are widely discussed but should not be.

2.2.1 Estonia’s I-Voting System

Estonia is the only country to have used internet voting nationwide across multiple parliamentary elections. Internet voting was offered in local elections from 2005 and in national parliamentary elections from 2007, and by the 2023 parliamentary election a majority of valid votes were cast online. The system relies on the national identity infrastructure: a voter authenticates with an identity card or mobile identity, both of which carry government-issued key material, so the hard problem of authenticating a remote voter has already been solved by a separate national programme.

Mechanism. The voter’s choice is encrypted in the client with the election public key and transmitted as an inner envelope, wrapped inside an outer envelope signed with the voter’s authentication key. The server strips the outer envelope at receipt, retaining a record that this voter has voted, and stores the inner envelope separately. After the close of voting, the inner envelopes are decrypted in a multi-party process and tallied through a mix-net.

Strengths. The two-envelope construction is the cleanest expression of what this project calls the secrecy boundary: the outer envelope carries identity, the inner envelope carries the choice, and the server deliberately destroys their association at the moment of receipt. Individual verification lets a voter check that their vote reached the server, and a mobile application allows re-verification in the final minutes of the voting period. Because internet votes are accepted before election day and a paper vote on election day supersedes them, the system does not disenfranchise a voter who changes their mind.

Limitations. The security model depends on a state-issued identity infrastructure that most countries do not have and that raises its own privacy questions. The published analyses of the Estonian system have consistently identified the client device as the weakest link: a compromised voter machine can display one choice and encrypt another, and no server-side control can detect it. Observers have also criticised the concentration of operational trust in the officials who run the key ceremonies.

Relevance to this project. Estonia demonstrates that the secrecy boundary should be a structural property of the data model rather than a procedural promise, which is the central design decision of Vote Anywhere. This project adopts the principle but not the mechanism: instead of two envelopes it uses two disjoint tables, which achieves the same separation without requiring an ElGamal cryptosystem.

2.2.2 Switzerland’s Cantonal E-Voting

Switzerland has the longest continuous e-voting programme of any democracy, and also the most instructive history of failure. E-voting is a cantonal competence rather than a federal one, so several systems have coexisted: the Geneva system, the Swiss Post system, and cantonal variants. Federal law permits e-voting only for a limited proportion of the electorate at a time, and every extension requires an independent audit.

Mechanism. The Geneva system used a verifiable scheme in which voters received a code sheet allowing individual verification of their encrypted vote on a public bulletin board, and universal verification allowed anyone to check that the published tally matched the published ballots. The Swiss Post system, developed later for commercial use by cantons, underwent a public intrusion test in 2019 in which participants were invited to attack the system; the test was successful in the narrow sense that it was conducted, and unsuccessful for the system in that severe vulnerabilities were found, leading to suspension.

Strengths. The Swiss approach institutionalised adversarial review. The requirement for an independent audit before each extension, and the practice of publishing source code and commissioning public penetration tests, set a standard that most e-voting programmes do not meet. The cryptographic design included individual and universal verifiability rather than merely encrypting traffic.

Limitations. The 2019 failure is the point of interest. The vulnerabilities found were not exotic breaks of the cryptographic primitives; they were implementation and infrastructure defects — insufficient hardening, inadequate separation of duties, and a development process that had not been subjected to adversarial review early enough. A system can have a sound cryptographic design and still be insecure because the code that implements it is not.

Relevance to this project. The Swiss experience is why Vote Anywhere states its non-goals so bluntly. A project that cannot afford an independent audit should not present itself as offering verified end-to-end integrity. What it can do is keep the attack surface small enough to reason about: one backend, nine modules, a schema whose invariants are visible.

2.2.3 New South Wales iVote

Australia’s New South Wales Electoral Commission operated iVote for state elections in 2011, 2015 and 2019 and for local government elections in 2021. Its distinguishing feature was the eligible population: iVote was restricted to voters who could not vote at a polling place — voters with disabilities, those outside the state or country, and those who would be more than a defined distance from a polling place. Scale grew sharply, reaching roughly a quarter of a million voters in 2015.

23

Strengths. iVote is the clearest example of remote voting targeted at the geographically mobile rather than at the whole electorate, which is precisely the population that Vote Anywhere models. It also demonstrated a practical telephone fallback: a voter without a suitable device could complete the process by telephone, which is a reminder that any remote voting scheme must have an assisted channel.

Limitations. The 2021 local government elections suffered a sustained outage during the voting period, and an independent review identified deficiencies in the verification of the system before deployment. A subsequent decision was taken to retire iVote in favour of telephone voting for the 2023 state election. University researchers had earlier published analyses questioning whether the verification mechanism provided the assurance it claimed, particularly where a voter’s device was compromised.

Relevance to this project. iVote shows that the eligible-population design decision matters as much as the technology. Restricting remote voting to a defined class of voter narrows the threat model and keeps the volume manageable. Vote Anywhere reflects this by requiring a reason on the remote polling request and by treating the assignment as a permission granted to a specific voter for a specific election, not as a general right.

2.2.4 India: Electronically Transmitted Postal Ballot and the Remote Voting Machine

India’s approach to the absent voter has historically been postal rather than electronic. The Electronically Transmitted Postal Ballot System, introduced for service voters, transmits the ballot electronically to the voter, who marks it, returns it by post, and has it counted at the returning officer’s centre. The system reduces transmission delay but retains a physical return, and it is restricted to defined categories such as members of the armed forces and government servants on election duty.

In January 2023 the Election Commission of India demonstrated a prototype Remote Voting Machine for domestic migrant voters. The device is a multi-constituency electronic voting machine: a single unit holds the candidate lists for many constituencies, and the presiding officer selects the constituency corresponding to the arriving voter’s registration before the voter casts a ballot. The Commission invited recognised political parties to a demonstration and stated that the concept required political consensus before any deployment.

Strengths. The multi-constituency machine addresses exactly the ballot-attribution problem that this project calls the Core Rule: the constituency is selected from the voter’s registration, not from the location of the machine. It also preserves the physical act of voting at a supervised centre, which retains the in-person identity check that postal balloting weakens.

2.2.5 The ETPBS Model Compared with a Remote Centre Model

Two families of solution therefore exist in the Indian context, and the difference between them determines the entire software design. In the postal model, the ballot travels to the voter and the voter is unsupervised when marking it; the system’s problem is delivering and returning a document. In the remote centre model, the voter travels to a supervised centre and marks the ballot there; the system’s problem is verifying entitlement and serving the correct ballot in a supervised location.

Vote Anywhere models the second family. This choice has three consequences that run through the whole report. Identity verification can be attached to an officer at a counter rather than to a document, which is why the project has a Polling Centre Officer role and a pre-vote verification screen. The ballot can be presented on a screen rather than posted, which is why the project has a controlled-ballot module rather than a document workflow. And the secrecy problem becomes a database problem rather than an envelope problem, because the officer who verifies identity is physically adjacent to the act of voting.

2.2.6 Verifiable Voting Research: Helios, Belenios and ElectionGuard

Alongside government deployments, an academic tradition has produced open, verifiable voting systems. Helios, published by Adida in 2008, was the first web-based open-audit voting system: ballots are encrypted with an ElGamal public key, a zero-knowledge proof demonstrates that each ciphertext encodes a valid choice, and a mix-net or homomorphic tally produces a result that any observer can check against the published ciphertexts. Helios has been used for low-stakes elections in universities, political parties and professional societies, exactly the setting where the threat model is modest.

Belenios extends this line with ballot receipts that a voter can use to check inclusion, and a registration mechanism designed to resist ballot-stuffing by the server, using a distributed key and credential derivation. It is used in French academic and institutional elections and has been studied extensively.

ElectionGuard is an open-source software development kit published by Microsoft that adds end-to-end verifiability to ordinary voting equipment using homomorphic encryption, with the explicit aim of producing a verifiable record that can be checked by members of the public without special software.

Strengths of this family. These systems are the only ones that give a mathematically stated guarantee rather than a procedural one. A Helios election can be verified by a third party who does not trust the operator, which is a genuinely stronger property than anything in this project.

Limitations. The guarantees concern the integrity of the tally, not the integrity of the voter’s device. All of them, and the literature is explicit about this, remain vulnerable to malware on the client that displays one candidate and encrypts another; coercion resistance requires additional machinery. Adoption has therefore been confined to elections where the stakes do not justify attacking the client. The systems also require the operator to run a key ceremony and to understand zero-knowledge proofs, which is a substantial operational burden.

Relevance to this project. These systems establish the vocabulary this report uses — individual verifiability, universal verifiability, receipt-freeness — and they establish the honest boundary. Vote Anywhere provides integrity of the stored ballot through authenticated encryption, and it provides secrecy by construction, but it does not provide end-to-end verifiability. Section 8.3 states this as a limitation in plain words rather than hiding it behind the word “encrypted”.

2.2.7 Blockchain Voting Proposals

A large and growing body of literature proposes blockchain-based voting, and a smaller but more rigorous body argues against it. The most cited critique, by Park, Specter, Koppel and Weitzner, is titled “Going from Bad to Worse”, and its argument is structural rather than cryptographic: a blockchain does not remove the need to trust the client device, the voter-registration process or the identity system, but it does add an immutable public record of ballots, which creates a new and serious coercion risk because a voter can be compelled to prove how they voted from a permanent ledger. Specter, Koppel and Weitzner made the complementary argument in their analysis of a widely piloted mobile voting application, showing that the vulnerabilities lay in the application and its infrastructure rather than in the ledger, which was doing no security work at all.

The consensus in the security literature is therefore that blockchain is not a solution to the voting problem and can be actively harmful. This project does not use one. The commitment is stated as a design decision rather than an oversight, and the glossary in the repository explicitly forbids the word.

2.2.8 Foundational Security Literature Applied in This Project

Four foundational results are used directly. Chaum’s 1981 paper on untraceable electronic mail introduced the mix-net, the idea that anonymity can be achieved by shuffling and re-encrypting a batch, and it is the intellectual ancestor of the two-envelope and two-table separation used here. Moran and Naor’s work on everlasting privacy establishes that information-theoretic secrecy can survive the later compromise of a key, a property this project does not attempt. Bernstein and Lange’s documentation of the NaCl cryptographic library, and the wider literature on misuse-resistant authenticated encryption, informed the decision to use AES-GCM through a standard library rather than any hand-written construction. Rogaway and Shrimpton’s formal treatment of authenticated encryption supplies the precise reason a hash alone is insufficient for ballot integrity: a party who can rewrite a stored ciphertext can rewrite a stored hash in the same write, whereas an authentication tag cannot be recomputed without the key.

Two practical standards shaped the implementation more than the research papers did. NIST SP 800-38D defines Galois/Counter Mode and, crucially, states the nonce-reuse hazard: reusing a nonce under the same key in GCM leaks the XOR of the two plaintexts and permits forgery of the authentication tag. This is why the code generates a fresh twelve-byte nonce from a cryptographically secure generator for every seal and never derives it from a reference or a counter. OWASP’s Application Security Verification Standard supplied the checklist against which the authentication and session handling were reviewed, in particular the requirement that a failure response must not disclose whether an account exists.

2.2.9 The Gap in the Literature

Three observations emerge from the review as a whole. First, the deployed systems are national infrastructure: they presuppose identity schemes, key ceremonies, independent audits and multi-party decryption, none of which is available to a student project, and each of which is itself a research programme. Second, the research systems are mathematically strong and operationally demanding, and their authors are careful to say that they do not solve the client-device problem. Third, and this is the gap, there is very little literature on the workflow layer: how an absent voter is verified at a counter, how an application is reviewed and decided, how a permission is granted and later consumed, and how the resulting administrative act is recorded.

29

That gap is not a gap in security research, because the security research community is rightly interested in the tally. It is a gap in the kind of system a public administration would need to deploy remote voting as a service. Estonia answered it with procedures surrounding the cryptographic core. iVote answered it with an eligibility test and a telephone fallback. The Indian Remote Voting Machine answers it with a physical multi-constituency device. None of them publishes a general, auditable workflow design that an undergraduate can read, run and test.

2.4 Research Gaps Identified

Six gaps follow from the review. Each is stated as a gap in what exists, then as the specific thing this project does about it, then as the honest limit of what has been achieved.

Gap 1 — The absence of a published, testable workflow design

Deployed systems publish architecture and audit reports, but not the ordinary state machine of an application: what states a request can occupy, which transitions are legal, who may cause each, and what must be true afterwards. That state machine is the part a smaller electoral authority would actually need to copy.

Addressed by: a seven-state request lifecycle with a single transition table, nine explicitly illegal moves each with a test, and five invariants that hold after every transition (Section 4.7.4 and Section 6.5).

Limit: the design is one plausible design, validated by internal consistency and tests, not by an electoral authority.

Gap 2 — Invariants stated in prose rather than enforced in structure

Most descriptions of remote voting state that the voter receives their own constituency’s ballot. Very few show a mechanism that makes any other outcome impossible. A comment is not an enforcement mechanism, and a validation check placed in one controller can be bypassed by a second controller written later.

Addressed by: removing the constituency from every input except the voter record. generateBallot takes a Voter; the assignment model has no constituency column; the remote-polling request stores a centre, never a constituency. There is no code path in which the remote centre’s constituency could reach ballot generation.

Limit: a future developer who adds a second ballot endpoint could reintroduce the defect. The regression test is the defence, and Section 7.4 explains why it is written as a named test rather than an incidental assertion.

Gap 3 — Secrecy described as policy rather than as schema

Systems frequently state that identity and choice are kept separate, while their schema contains a voter identifier on the ballot row. The separation then depends on the discipline of every developer who writes a query.

Addressed by: two tables with no key in common, no relation in the object-relational mapping, and a test that asserts the absence of any voter-referencing column on the ballot table.

Limit: timing correlation, as noted in Section 2.3.2.

34

Gap 4 — Duplicate prevention placed in application code

A proportionate amount of tutorial and project material implements duplicate prevention as a read followed by a conditional write. This is correct in a single-threaded demonstration and incorrect under concurrency, which is precisely when it matters. Published analyses of real systems have repeatedly found check-then-act races in registration and issue paths.

Addressed by: a unique constraint on (voterId, electionId) in the identity-side table, and a test that fires two submissions concurrently and asserts that exactly one succeeds. The service translates the constraint violation into a domain error; the constraint is the enforcement.

Limit: the guarantee is per database. A future sharded deployment would need a different mechanism, which is noted as future work.

Gap 5 — Audit trails that leak the thing they audit

Audit requirements are often written as “record everything”. Recording everything in an election includes recording the choice and the credential, which turns the audit trail into the most sensitive table in the system. The literature on election audit is aware of this; student implementations usually are not.

Addressed by: an audit schema with five columns and no free-text payload, a naming convention for actions, a rule that the ballot submission audit record carries the opaque ballot reference and a system actor rather than the voter, and a test that asserts no code, password or key material appears in any record.

Limit: records are append-only by construction but not tamper-evident; a party with direct database access could alter them.

Gap 6 — Proportionate complexity for a teaching context

The systems that solve the problem properly cannot be read in a semester. The systems that can be read in a semester usually omit the invariants. There is little middle ground: a complete, runnable, test-covered system whose entire design fits in one report.

Addressed by: this report and the repository it documents — nine backend modules, twenty-eight tests, and a schema of fourteen models in which every model carries a comment naming the invariant it protects.

Limit: a teaching system is not a deployment. Section 8.3 lists what would be required before it could be considered for any real use.

2.5 Summary of Literature Review

The literature and the deployed record together support five conclusions, which shaped the design decisions recorded in Chapters 3 and 4.

2.5.1 Findings

  1. Remote voting is a solved problem only where an identity infrastructure already exists. Estonia’s success is inseparable from its national identity card. Where such infrastructure is absent — which is most places — the authentication problem dominates, and a project that cannot solve authentication must simulate it and say so.
  2. Ballot secrecy is best achieved structurally. Every system that is taken seriously separates identity from choice at the level of the artefact, whether that artefact is an envelope, a mix-net batch or a table. Procedures that rely on officials not looking at two things at once are the weakest of the available options.
  3. The client device is the unsolved weakness across all families. Every system reviewed, from Estonia to Helios, is vulnerable to a compromised client that displays one choice and records another. This project inherits the weakness and does not mitigate it; the honest response is to say so, which Section 8.3 does.
  4. Verifiability and simplicity trade against each other. End-to-end verifiable systems are stronger but require cryptography, ceremonies and specialist review. A system without those resources should not claim verifiability; it should claim what it can demonstrate.
  5. The workflow layer is underexploited as a subject of study. The literature is rich on tally integrity and thin on the administrative state machine that surrounds it: application, review, approval, assignment, consumption, reconciliation. That is the layer this project occupies.

2.5.2 Position of the Present Work

Vote Anywhere does not compete with Estonia, Helios or the Indian Remote Voting Machine on any axis of cryptographic strength. It is not verifiable end to end, it does not resist a compromised client, and its identity scheme is a simulation. What it offers is a complete, runnable, tested implementation of the workflow layer, in which the two central invariants are enforced structurally and can be confirmed by reading a single schema file.

Stated as a claim: a small team can implement the administrative workflow of remote polling in a way that makes the Core Rule and ballot secrecy properties of the data model rather than promises of its operators, and can demonstrate that this is so with automated tests. Chapters 3 to 7 defend that claim. Chapter 8 assesses how far it succeeds.

3.1 Existing System Analysis

Before designing anything it is necessary to describe how the process works today, in the absence of the proposed system, and to describe it without caricature. The existing system for an absent voter in India is not an absence of process; it is a set of processes with different scopes, different eligibility tests and different degrees of automation. Vote Anywhere positions itself against three of them.

3.1.1 Existing Process A — The Voter Travels

The default answer for a voter who is away from their constituency is that they travel back. The process is entirely offline and entirely manual:

  1. The voter learns the poll date, usually from the press or a mobile application.
  2. The voter arranges travel to the constituency in which they are enrolled.
  3. The voter appears at their assigned polling station on the poll date with an approved identification document.
  4. The presiding officer locates the voter’s entry on the printed electoral roll, checks the identification, applies indelible ink to the finger and obtains a signature or thumb impression on the register.
  5. The voter proceeds to the voting compartment and records the choice on the ballot unit or paper ballot.
  6. The ballot is deposited in the ballot box; the voter leaves.

This process is reliable, supervised and auditable, and it is the baseline the proposed system must not degrade. Its characteristic failure for the population in question is that steps 2 and 3 require a journey that may cost more than the voter can justify for a single vote: a day of wages, a night of travel, and a fare that may be a substantial fraction of a month’s income. The result is not a formal refusal but a quiet abstention, which is why the scale of the problem is not visible in election statistics.

38

3.1.2 Existing Process B — Postal Ballot for Eligible Categories

For defined categories — service voters, electors subject to preventive detention, and electors on election duty — a postal ballot is available. The Electronically Transmitted Postal Ballot System transmits the ballot to the voter electronically and the voter returns it physically. The process runs as follows:

  1. The returning officer identifies the electors in the eligible categories from the roll.
  2. A ballot, a declaration and a covering envelope are prepared for each such elector.
  3. The material is transmitted, in the electronic variant by secure channel.
  4. The voter marks the ballot, completes the declaration, seals the ballot in the covering envelope and places both in the outer envelope addressed to the returning officer.
  5. The outer envelope is returned by post and received at the returning officer’s centre, where the declaration is verified before the covering envelope is opened.
  6. Postal ballots are counted at a designated centre.

The design is careful. The covering envelope exists precisely so that the ballot can be separated from the declaration before counting, which is the procedural equivalent of the secrecy boundary. The characteristic failures are time and eligibility: the postal channel is slow, the return must arrive before the count, and the eligible categories are narrowly defined. A student who has moved cities for a degree is not a service voter and has no access to this route.

3.1.3 Existing Process C — Informal Permission

In practice a fourth process exists, unofficially. A voter who is known to a local official may obtain an informal accommodation: a message, a phone call, an understanding that they may present themselves at a nearby centre. This is not a legitimate process and no electoral authority sanctions it, but it is the observable behaviour that a formal system would replace.

Its weaknesses are total. There is no record of the permission, no verification of eligibility at the destination, no assurance that the correct ballot is served, no prevention of a second vote at the home centre, and no audit trail. It is mentioned here for a specific analytical reason: the existence of informal arrangements demonstrates demand. A workflow with these weaknesses is preferable to the status quo from the perspective of an administrator who wants accountability, which is the argument the proposed system makes.

  • Counting is observable. A counting agent can watch every ballot being counted. Aggregate results from a decryption routine are less observable, even when the routine is correct.

3.2 Limitations of Existing System

The limitations are grouped by the party who experiences them, because the same defect can be trivial for one party and decisive for another.

3.2.1 Limitations for the Voter

L1 — Cost exceeds benefit. The travel process is valid only if the voter can afford the journey. For a low-wage migrant worker, a return fare and a lost day’s wages can exceed a week’s income, which makes abstention economically rational. The system offers no alternative.

L2 — No route for the ordinary migrant. Postal balloting is restricted by category. A student, a software professional on a project posting, or a patient receiving treatment in another city is outside every defined category and has no legitimate route at all.

L3 — No visibility of the process. There is no way for a voter to know in advance whether they will be accepted at a centre, what documentation to bring, or what the outcome of any application is. The process is discovered by asking, and the answer depends on whom one asks.

L4 — No receipt. After voting, a voter has no artefact other than the ink mark. This is a deliberate feature of the secret ballot, not a defect, but it leaves the voter with no way to demonstrate that a problem occurred.

3.2.2 Limitations for the Administrator

L5 — No instrument for the demand. Because the affected voters simply do not appear, the administration has no data on how many voters are absent from their constituency during a poll. Planning is therefore based on estimates rather than measurements. A request workflow produces exactly this data as a side effect.

L6 — No authorisation record. Any accommodation granted informally leaves no record, so it cannot be reviewed, counted, or defended if the result is challenged.

L7 — No reconciliation instrument. There is no procedure that compares, for an absent-voter scheme, the number of ballots issued against the number recorded. The existing processes reconcile by physical custody: ballots are counted, and the count is checked against the issue register at one place. A distributed scheme needs a different instrument.

L8 — Duplicate risk is unmanaged. A voter who is informally permitted to vote at another centre might also appear at their home centre. The ink mark is the only control and it is applied at the point of the second appearance, if at all.

42

3.2.3 Limitations in the Technology Dimension

L9 — Nothing to audit. The most consequential limitation is not a defect in any process but the absence of a digital artefact. A database record with a timestamp and an actor can be queried, aggregated, exported and reviewed; a telephone call cannot. Any improvement in accountability requires that the administrative act leave a trace, and that requires software.

L10 — No separation of duties. In an informal arrangement, the same person who decides that a voter may vote remotely is likely also the person who knows how that voter voted, because both happen in front of them. A designed workflow can separate these roles: one officer approves, a different officer verifies at the centre, and neither can see a choice.

L11 — No defined failure behaviour. Every manual process fails in an undefined way. If the officer who granted the accommodation is unavailable, nothing happens. If the centre has no ballot for the voter’s constituency, the voter is turned away. Software can specify the failure: an election that has closed refuses new requests with a stated reason rather than a shrug.

3.3 Proposed System

The proposed system is a web application that implements the remote-centre model described in Section 2.2.5. It provides a request-and-approval workflow that produces an authorisation artefact, a controlled ballot that is generated from the voter’s registered constituency, a submission path whose integrity can be verified, and a set of reports that close the administrative loop.

3.3.1 System Description

The system is a modular monolith. A React and TypeScript single-page application runs in the browser and communicates over HTTP with a single Express service written in TypeScript. The service is divided into nine domain modules — authentication, voters, elections, remote polling, ballots, the Election Simulator, officer support, administration and audit — and each module is further divided into a route layer, a service layer and a repository layer. Persistence is PostgreSQL 16, accessed through Prisma 6, with schema changes delivered as versioned SQL migrations. PostgreSQL runs in a Docker container during development; the two application processes run on the host.

The role model has five members. Voters authenticate with a mock one-time password and act only on their own records, identified from the session and never from a request parameter. Verification Officers review and decide remote polling requests. Polling Centre Officers verify arriving voters and control ballot issuance. Election Administrators configure and operate elections and read reports. System Auditors read the audit trail and the reconciliation report and may write nothing.

45

3.3.2 The Workflow in Nine Steps

  1. Authenticate. The voter submits a voter number and receives a six-digit code through the development channel. The code is stored as a bcrypt hash with a five-minute expiry and a five-attempt cap.
  2. Verify eligibility. The voter runs an eligibility check that reports four conditions separately: the voter record is active, the election covers the registered constituency, the election is not closed, and no ballot has been submitted.
  3. Submit a request. The voter selects a polling centre outside their registered constituency and may give a reason. The request is created in the PENDING state.
  4. Review. A Verification Officer claims the request, which moves it to UNDER_REVIEW and records the reviewer.
  5. Decide. The officer approves, which creates the assignment in the same transaction, or rejects with a mandatory reason which is shown to the voter.
  6. Verify at the centre. A Polling Centre Officer looks up the voter number and sees the request, the assignment and whether the voter has already voted.
  7. Cast the ballot. The voter is shown the candidates of their registered constituency and submits one choice. The choice is sealed; an opaque reference is returned.
  8. Reconcile. After closure, the administrator and the auditor compare ballots issued against ballots recorded, per constituency.
  9. Report. Aggregate results per candidate per constituency become available to every authenticated role.

A1 — The correct ballot is structurally guaranteed. The ballot service accepts a complete voter record, so the constituency it uses cannot be supplied by a caller. The assignment record has no constituency column, so no approved permission can carry one. Even a request that forges a candidate identifier is rejected, because the candidate must stand in the voter’s registered constituency for that election.

A2 — Duplicate voting is impossible, not merely unlikely. The unique constraint on (voterId, electionId) is evaluated by the database inside the transaction. Two simultaneous submissions cannot both succeed; the second receives a conflict and the first remains the only record.

A3 — Request state cannot drift. All transitions pass through one table. A rejected request cannot become approved; a used request cannot be reopened; a pending request cannot skip review. Each refusal is tested.

A4 — Approval and assignment cannot diverge. Both writes occur inside one transaction, so an approved request always has exactly one assignment and no assignment exists without an approved request.

A5 — Ballot integrity is verifiable without disclosure. Verification is a decryption attempt that returns a boolean. It is impossible for the verification path to return a choice, because its return type says so.

3.4.2 Secrecy Advantages

A6 — Voting records and vote records cannot be joined. Two tables, no common key, no relation. The property is visible in the schema and asserted by a test.

A7 — The audit trail cannot become a leak. The audit schema has five columns and no free-text payload. The ballot submission record names a system actor and an opaque reference. A test asserts that no code, password or key is ever written.

A8 — Results are aggregates by construction. The results routine returns counts per candidate per constituency. There is no code path that emits a per-voter result, because the choice table could not support one.

50

3.4.3 Operational Advantages

A9 — Authorization is enforced server-side with deny-by-default semantics. Each route names the roles permitted to reach it. A role that is added to the system later has access to nothing until it is explicitly named, and a hidden button is never the control.

A10 — Every state change is attributable. Each transition writes an audit record naming the actor type, the actor, the action and a reference to the operation. Election closure writes system-actor records for each expiring request, so the batch operation is visible rather than silent.

A11 — Failure is defined and non-disclosing. Every domain error carries a stable code and a human message. Authentication failures are uniform across unknown account, wrong credential, expired code and consumed challenge, and the failure path executes a bcrypt comparison against a dummy hash so that response timing does not disclose which case occurred.

A12 — The system is reproducible and inspectable. One documented sequence of commands produces a running system with fictional data. The schema carries a comment on every model naming the invariant it protects, which means a reviewer can confirm the design in one file.

3.5 Feasibility Study

A feasibility study answers three questions: can it be built, can it be afforded, and will it be used. Each is treated separately because they fail for different reasons.

3.5.1 Technical Feasibility

The technical question is whether the required behaviour can be built with the technologies available to a single student within one semester. Five technical requirements were examined.

T1 — Can the invariant be enforced in the schema? Yes. Relational databases support unique constraints, partial unique indexes and composite foreign keys, and the project uses all three. The one construct Prisma cannot express — a partial unique index — is written as raw SQL inside a migration, which is a documented and supported practice.

T2 — Can authenticated encryption be implemented without writing cryptography? Yes. node:crypto provides AES-256-GCM. The project supplies a key, a fresh nonce and associated data, and delegates the rest. The total cryptographic code is approximately ninety lines including comments.

T3 — Can role-based authorization be enforced centrally? Yes. Two small middleware functions, requireRole and requireVoter, are placed on each route. Because they are explicit allow-lists, the default for an unlisted role is refusal.

T4 — Can the invariants be tested? Yes, and this was decisive. Supertest drives the real HTTP layer and Jest asserts on the responses, against a real PostgreSQL instance that enforces the constraints. An in-memory substitute would have made the constraint tests vacuous.

T5 — Is the required tooling available and free? Yes. Every tool in the stack — Node.js, Express, Prisma, PostgreSQL, React, Vite, Tailwind, Jest, Docker — is open source and runs on an ordinary laptop.

Conclusion. Technically feasible without qualification. The only genuine technical risk identified at the outset was the partial unique index, and it was resolved in the first migration by writing raw SQL. The remaining risk is not capability but time, which is addressed in Section 3.5.3.

3.5.3 Operational Feasibility

Operational feasibility asks whether the people who would use the system can and will use it. Four groups were considered.

Voters. The voter journey requires three interactions: entering a voter number to receive a code, choosing a centre from a list, and selecting a candidate. Each is a single screen, and the interface uses a stepper that shows the voter where the request stands. The principal operational risk is the one-time code: any real deployment would need a delivery channel, and the mock channel used here is not one. This is the largest operational gap in the project and is stated as such.

Verification Officers. The review queue is a filtered list with a status badge and a detail panel. The officer’s task is to read the voter’s reason and decide. The system does not present eligibility evidence beyond the voter record, so a real deployment would need an evidence panel. The operational burden is low: a decision is two clicks in the common case.

Polling Centre Officers. The verification screen takes a voter number and returns the voter’s record, request status, assignment and whether they have already voted. This is the digital analogue of the Form 17A check and fits the existing workflow of a presiding officer rather than replacing it.

Administrators and auditors. Both roles are read-mostly. The administrator activates and closes elections and reads reports; the auditor reads the trail. Neither requires training beyond a walkthrough.

Organisational feasibility. The deeper operational question is political rather than technical: any change to how votes are cast requires consensus among political parties, and the Indian Remote Voting Machine prototype is explicitly waiting on that consensus. A student project cannot create that consensus, and the report does not pretend otherwise. What a project can do is demonstrate that the technical objections — constituency corruption and secrecy loss — have technical answers, and thereby narrow the argument to the political question where it belongs.

4.1 Design Overview

Design is where a requirement becomes a structure. The requirements in Section 3.6 say that the correct ballot must be served and that secrecy must survive the remote act; this chapter says how, in terms of modules, data flows, classes and tables. It is the longest chapter of the report because it carries the argument the project is making.

4.1.1 Design Principles

Six principles governed every structural decision. They are stated first because each later choice can be traced to one of them.

P1 — Make the invariant unrepresentable, not merely checked. If the wrong value cannot be expressed, no check is required. This principle explains why generateBallot takes a Voter, why the assignment model has no constituency field, and why the choice table has no voter column.

P2 — Put consistency where concurrency happens. A check in application code is correct only until two requests arrive together. Anything that must be true across concurrent writers belongs in the database: a unique constraint, a partial index, a foreign key or a transaction.

P3 — One legal path per state change. Rather than scattering conditionals, every request transition passes through a single table and a single guard. Adding an illegal transition then requires editing the table, which is a visible act rather than an accidental omission.

P4 — Deny by default. Authorization is an explicit allow-list per route. A role that is not named has no access, so adding a role later grants it nothing by default.

P5 — Separate the layers by responsibility, not by ceremony. Routes parse and respond, services decide, repositories persist. There is no Prisma call in a service and no HTTP concern in a repository. The boundary is enforced by review rather than by a framework, and the codebase is small enough for that to work.

P6 — The schema is the documentation of last resort. Comments go out of date; constraints do not. Every model in schema.prisma carries a doc comment naming the invariant it protects, so that a reader who opens one file understands the design.

4.2 System Architecture

The application follows a three-tier layered architecture deployed as a modular monolith. That phrase contains two decisions that should be separated: the layering, which is about responsibility, and the monolith, which is about deployment.

4.2.1 The Three Tiers

Presentation tier. A React 19 single-page application, written in TypeScript and built by Vite. It holds no business rule that matters. It validates forms for the convenience of the user, guards routes so that a voter does not see officer screens, and renders what the API returns. Every one of these behaviours is a courtesy; the server does not rely on any of them.

Application tier. One Express 4 process, written in TypeScript, containing nine domain modules. Each module has a router that declares paths and middleware, a service that holds the decisions, a repository that holds the queries and, where input arrives, a Zod schema that validates it at the edge. Cross-cutting concerns — authentication, authorization, validation, rate limiting and error translation — are middleware, so they appear in the route declaration rather than inside the logic.

Data tier. PostgreSQL 16 through Prisma 6. This tier is where the invariants that must survive concurrency actually live. The application asks the database to enforce them and translates the resulting errors into domain errors; it does not re-implement them.

4.5.2 Rationale for the Class Structure

Five features of the class structure deserve comment, because each is a decision rather than an accident of modelling.

No inheritance is used. A conventional object model might introduce a base Actor class with Officer and Voter as subclasses. This design does not, and the reason is concrete: the two actors have entirely different authentication mechanisms, different session semantics and different lifecycles, and the only thing they share is that both produce a session. That shared fact is represented in Session, which carries an actorType discriminator and two optional foreign keys. The result is a shallower hierarchy and a simpler query, at the cost of two nullable columns — a trade judged worthwhile because the nullability documents precisely which combinations are legal.

ElectionConstituency is an association class with a primary key, not a bare join table. It carries a composite primary key on the pair, which means the pair can be referenced as a whole. That capability is used: Candidate has a composite foreign key to (electionId, constituencyId), and the effect is that a candidate cannot be created for a constituency that is not part of the election. The constraint is expressed once, in the schema, and holds for every insert regardless of which code path performs it.

The assignment has no constituency attribute. This is the single most important absence in the diagram. An approved assignment tells a voter which centre they may attend and which election it concerns. It says nothing about which ballot they will receive, because that is determined by the voter record alone. A modeller who added constituencyId here for convenience would make the Core Rule a runtime check rather than a structural fact.

SubmittedBallot has no voter attribute. It has a ballot reference, an election, a constituency and three cryptographic fields. There is no voter identifier and no relation by which one could be reached. The diagram shows the class floating free of the identity side, which is the visual statement of the secrecy boundary.

AuditRecord references entities by string, not by foreign key. This is intentional. A foreign key would create a referential constraint that would prevent the audit trail from outliving the record it describes, and it would also invite joins that reconstruct the very relationships the audit design avoids. The entityRef is an opaque string: a voter identifier for a voter action, a request identifier with its transition for a state change, a ballot reference with a system actor for a submission. The audit trail therefore records facts about operations without becoming a graph of the system.

4.6.3 The Core Rule in the Schema

The Core Rule states that a remote polling centre changes where a voter votes and never changes the registered constituency or the ballot received. Three schema facts enforce it, and none of them is a comment.

Fact one. Voter.registeredConstituencyId is a non-nullable foreign key, and it is the only place the association between a voter and a constituency is stored as an enrolment. No other table records an alternative.

89

Fact two. RemotePollingAssignment contains pollingCentreId and contains no constituency column. To discover the ballot for an assigned voter, a query must go through Voter.registeredConstituencyId, because that is the only path the schema offers.

Fact three. SubmittedBallot.constituencyId is written from voter.registeredConstituencyId at submission time, and the service that writes it never receives a constituency as input. Reconciliation then compares counts grouped by the same value, so a ballot cast at a remote centre is counted towards the voter’s own constituency rather than the centre’s.

4.6.5 Cardinality Under the Secrecy Boundary

The secrecy boundary produces an unusual situation in relational terms: two tables that are conceptually related by a single real-world event but have no join path. The relation between them exists only as a fact outside the database — the same person performed both writes in the same transaction.

91

This is not a normalisation defect. It is the deliberate removal of a functional dependency that the system must not be able to compute. A database theorist would say that the relation “which voter cast which ballot” is held in the operator’s memory and in the wall-clock ordering of transactions, and deliberately not in the schema. Anything that could reconstruct it — a shared nonce, a timestamp precise enough to correlate, a sequence number — has been avoided. The ballot reference is random and non-sequential precisely so that it orders nothing.

4.7.9 The Partial Unique Index

One constraint deserves separate treatment because it is the only piece of the schema that Prisma cannot express. The rule is: a voter may hold at most one active request per election, where active means PENDING or UNDER_REVIEW. A voter may hold any number of historical requests in terminal states, because a rejected or withdrawn application must not prevent a new one.

A plain unique index on (voterId, electionId) would be wrong, because it would also forbid a second request after the first was rejected. A check in application code would be wrong, because two concurrent submissions could both pass it. The correct instrument is a partial unique index, which applies uniqueness only to rows matching a predicate.

-- backend/prisma/migrations/20261030175226_init/migration.sql
-- At most one active (PENDING or UNDER_REVIEW) remote polling request per
-- voter per election. Prisma cannot express partial indexes, so this is
-- hand-written; the constraint name must never reach a response body.
CREATE UNIQUE INDEX "RemotePollingRequest_one_active_per_voter_election"
ON "RemotePollingRequest" ("voterId", "electionId")
WHERE "status" IN ('PENDING', 'UNDER_REVIEW');

Three consequences follow. First, the database now refuses a second active request even if the service layer is bypassed, which is the property a constraint is for. Second, the service must translate the resulting error code, P2002, into a domain error, because a raw constraint violation must never reach a client. Third, the index is invisible to Prisma’s schema-diffing, so a future developer who regenerates the schema will not produce this index and must be told about it — which is why the index carries a comment in the migration and is named in Appendix A.

4.8 Input and Output Design

Input and output design governs what a user is asked for, in what order, and what they are shown in return. Two rules were applied throughout. Ask only for what the server needs and cannot derive, and show the derived value back so that the user can see that the system understood.

4.8.1 Input Design Principles

Derive rather than ask. The voter is never asked for their voter identifier when submitting a request or a ballot; it comes from the session. The voter is never asked for their constituency; it is shown, not requested. The officer is never asked which election they are acting on when the concept of a current election applies.

Constrain at the edge. Every endpoint that accepts a body or a query parameter declares a Zod schema. The schema runs before the handler, so a malformed identifier is refused with a 400 before any database work happens. The schemas are small and literal: a UUID, a bounded string, an enum member.

Label the consequence. The centre-selection list shows each centre with its constituency, so that a voter can see that the centre they are choosing is outside their own constituency before they submit. The interface does not hide the rule; it explains it at the moment of choice.

Refuse with a reason. A refusal that says “invalid request” teaches nothing. The domain errors in this system carry a sentence: choose a polling centre outside your registered constituency — your home centre is the default is more useful than 422, and it is what the code actually returns.

4.8.9 Design Summary

Chapter 4 has established eight things. An architecture of three tiers deployed as a modular monolith, chosen for transactional integrity. A request path in which authentication, authorization, validation and error translation are all middleware, and in which revocation is immediate because the session row is re-read on every request. Three levels of data flow, of which the significant feature is a non-arrow between the identity store and the choice store. A use case model with five actors and a realisation matrix that maps every use case to a route and a method. A class model in which the two most important facts are absences: the assignment has no constituency and the ballot has no voter. An entity-relationship model with fifteen relationship lines, of which one is deliberately missing. A database design in which four constraints carry the invariants that matter, including one hand-written partial index. And an input-output design in which the ballot screen explains the Core Rule to the voter at the moment it matters.

The design decisions that a reader should carry into Chapter 5 are these:

  • The Core Rule is enforced by a function signature and by two absences in the schema, not by a validation check.
  • Duplicate ballots are prevented by a unique constraint evaluated inside a transaction, not by a read-then-write.
  • The transition table is the single source of legality for request state changes.
  • The assignment and the approval are written in one transaction because an approved request without an assignment is an incoherent state.
  • The secrecy boundary is a schema boundary: two tables, no key, no relation.
  • Authorization is an explicit allow-list on every route, so the default is refusal.
  • Ballot verification returns a boolean and counting is a separate function, so the verification path has no type-level way to disclose a choice.

Chapter 5 turns to the technology stack that implements this design, and Chapter 6 to the implementation itself — the modules, the algorithms, the pseudocode and the code sketches.

5.3 Languages Used

Four languages appear in the repository: TypeScript for all application code, SQL inside migrations, CSS through Tailwind, and Markdown for documentation. Each is used where it is strongest.

5.3.1 TypeScript

TypeScript 5.7 is used for the backend, the frontend and the tests. The decisive reason is not developer convenience but the class of error it removes. In a system whose central property is a boundary that must not be crossed, a compiler that knows the shape of a SubmittedBallot and refuses to accept a voter identifier in the function that creates one is worth more than any amount of prose. Three specific uses of the type system matter:

Discriminated session types. The session payload is a union of an officer session, a voter session and a system actor, distinguished by actorType. A handler that reads officerId must first narrow to the officer variant, so a voter session cannot be read as an officer session by accident.

Literal union statuses. The seven request statuses are a union of string literals generated from the Prisma enum. The transition table is typed as a record from every status to an array of statuses, so an illegal target cannot be written without a type error.

Function signatures as policy. generateBallot(voter: Voter) and sealChoice(choice: string, ballotReference: string, electionId: string, constituencyId: string) are both signatures in which the Core Rule is encoded. The first takes a whole Voter object rather than a loose constituency identifier, which is deliberate: a caller cannot supply a constituency at all, even by mistake. Widening either signature is a visible act in a code review.

5.5.4 Configuration Management

Configuration is separated into three classes, and only the first is committed.

Committed defaults. .env.example lists every variable with a comment explaining how to produce a valid value. 6.1.1 The Boundary Between remote-polling and ballots

These two modules carry the design. remote-polling answers may this voter vote somewhere else. ballots answers what may this voter choose. The separation is not organisational tidiness; it is the reason the Core Rule holds. 6.2 Algorithms

Four algorithms carry the guarantees. Each is stated as a procedure with its invariants, followed by its complexity.

6.2.1 Controlled Ballot Generation

Purpose. Return the candidates a voter may choose, drawn only from the voter’s registered constituency, together with the election context and, if one exists, the approved remote assignment.

GENERATE-BALLOT(voterId)
 1  voter ← find voter by id, including registeredConstituency and homePollingCentre
 2  if voter = ∅ then error NOT_FOUND
 3  election ← the single election whose lifecycle ≠ CLOSED
 4  if election = ∅ then error NO_ACTIVE_ELECTION
 5  if election.lifecycle ≠ ACTIVE then error ELECTION_NOT_ACTIVE
 6  if VoterElectionStatus(voterId, election.id).hasVoted then error ALREADY_VOTED
 7  constituency ← voter.registeredConstituencyId        ▷ the ONLY source
 8  candidates ← Candidate where electionId = election.id
 9                              and constituencyId = constituency
10  assignment ← RemotePollingAssignment(voterId, election.id) or ∅
11  return { election, constituency, candidates, assignment }

 Invariant: the value bound at line 7 is taken from the voter row and from
 no other relation. There is no parameter by which a caller could supply a
 different constituency, and the assignment read at line 10 is used only to
 display a centre name — never to derive a ballot.

Complexity. Four indexed lookups and one join, all on primary or unique keys; O(log n) per lookup, dominated by network round trips rather than by the database.

6.2.2 Sealing a Choice

Purpose. Convert a candidate choice into three fields that cannot be read without the key, and that cannot be transplanted from one ballot to another.

SEAL-CHOICE(choice, ballotReference, electionId, constituencyId)
 1  key   ← decode BALLOT_ENCRYPTION_KEY (64 hex → 32 bytes)
 2  nonce ← crypto.randomBytes(12)                 ▷ fresh, never reused
 3  aad   ← "ballotReference|electionId|constituencyId"
 4  cipher ← createCipheriv("aes-256-gcm", key, nonce)
 5  cipher.setAAD(utf8(aad))
 6  ciphertext ← cipher.update(utf8(choice)) ‖ cipher.final()
 7  tag ← cipher.getAuthTag()
 8  return { nonce, ciphertext, tag }

 Rationale for the associated data: a ciphertext lifted from ballot A and
 written onto ballot B would decrypt successfully if only the choice were
 authenticated. Binding the reference, election and constituency makes a
 transplanted ciphertext fail authentication at line 7 of OPEN-BALLOT.

Open versus verify. Two functions read a sealed ballot. verifyBallotIntegrity() returns a boolean and never returns plaintext; it is the only function available to any path that is not counting. openBallotForCounting() returns the plaintext and is called from one place, simulatorService.results, after the lifecycle check. The type system enforces the separation because the two functions have different return types and neither is exported from the ballot module’s public surface except to the simulator.

124

6.2.3 Ballot Submission Under Concurrency

Purpose. Accept at most one ballot per voter per election, even when two requests arrive in the same millisecond, and leave the identity side and the choice side consistent.

SUBMIT-BALLOT(voterId, candidateId)
 1  election ← active election; if none or CLOSED → error
 2  status   ← VoterElectionStatus(voterId, election.id)
 3  if status ≠ ∅ and status.hasVoted → error ALREADY_VOTED      ▷ fast path
 4  voter    ← voter with registeredConstituency
 5  candidate ← candidate where id = candidateId
 6  if candidate = ∅ or candidate.constituencyId ≠ voter.registeredConstituencyId
 7      or candidate.electionId ≠ election.id → error INVALID_CHOICE
 8  reference ← hex(randomBytes(16))                              ▷ opaque
 9  sealed    ← SEAL-CHOICE(candidateId, reference, election.id,
                            voter.registeredConstituencyId)
10  BEGIN TRANSACTION
11      if status = ∅
12          INSERT VoterElectionStatus{voterId, electionId, hasVoted=true, votedAt=now}
13      else
14          UPDATE VoterElectionStatus SET hasVoted=true, votedAt=now
15              WHERE id = status.id AND hasVoted = false       ▷ guarded
16      if rowsAffected = 0 → ROLLBACK; error ALREADY_VOTED
17      INSERT SubmittedBallot{reference, electionId,
              constituencyId = voter.registeredConstituencyId,
              nonce, ciphertext, tag, submittedAt = now}
18      UPDATE RemotePollingRequest SET status = "USED"
              WHERE voterId = voterId AND electionId = election.id
              AND status = "APPROVED"
19  COMMIT
20  return { ballotReference: reference, submittedAt }             ▷ no choice
 ON CONFLICT (unique violation P2002) → error ALREADY_VOTED

Why the guard is in the database. The read at line 3 is a fast path that produces a friendly error in the common case, but it is not the guarantee. The guarantee is the unique index on (voterId, electionId) and the guarded update at line 15: if two transactions interleave, exactly one commits and the other receives a unique violation at line 17 or loses the row-level race at line 15. The application converts that violation into the same domain error, so the caller cannot distinguish which mechanism caught them.

Why the request is marked USED inside the transaction. A request marked USED outside the transaction could survive a rolled-back ballot, leaving a voter who has not voted holding a spent permission. Inside, the two facts are written or not written together.

RECONCILE(electionId)

 The report contains counts only. No ballot reference, no voter, and no

In a correct run every discrepancy is zero, because lines 12–17 of the submission transaction write both sides. A non-zero value is therefore evidence of a defect or of a row inserted outside the application, which is exactly what the report exists to detect.

6.3 Pseudocode of the Request State Machine

The transition table is one constant. Every mutation passes through the guard below, so legality is decided in one place.

TRANSITIONS = {
  PENDING       : [UNDER_REVIEW, WITHDRAWN, EXPIRED],
  UNDER_REVIEW  : [APPROVED, REJECTED, WITHDRAWN, PENDING, EXPIRED],
  APPROVED      : [USED, EXPIRED],
  REJECTED      : [], WITHDRAWN : [], USED : [], EXPIRED : []
}

TRANSITION(requestId, target, actor)
 1  request ← find by id; if ∅ → NOT_FOUND
 2  if target ∉ TRANSITIONS[request.status] → error ILLEGAL_TRANSITION (409)
 3  if actor is a voter and request.voterId ≠ actor.id → NOT_FOUND   ▷ not 403
 4  if target = APPROVED
 5      if election.lifecycle = CLOSED → error ELECTION_CLOSED
 6      if VoterElectionStatus(voter, election).hasVoted → error ALREADY_VOTED
 7  if target = REJECTED and trim(reviewNote) = "" → error REASON_REQUIRED
 8  BEGIN TRANSACTION
 9      UPDATE request SET status = target, reviewedById = actor, reviewedAt = now
10      if target = APPROVED
11          INSERT RemotePollingAssignment{requestId, voterId, electionId,
                     pollingCentreId = request.pollingCentreId, assignedById}
12      if target = REJECTED
13          UPDATE request SET reviewNote = note
14  COMMIT
15  AUDIT(actor, "REMOTE_REQUEST_" + target, requestId)
16  return updated request

Three details are deliberate. Line 3 returns NOT_FOUND rather than FORBIDDEN when a voter addresses someone else’s request, so the API does not confirm that the identifier exists. Lines 10–11 create the assignment inside the same transaction as the status change, which is what makes INV-1 (an approved request has exactly one assignment) a property of the database rather than of a subsequent call. And line 15 writes the audit record after the commit: if the audit write failed first, a committed transition could exist with no record, whereas an audit write that fails after the commit loses a record but leaves the system consistent. Neither ordering is perfect; the chosen one prefers consistency of domain state over completeness of the log, a trade recorded in Section 8.3.

OFFICER-LOGIN(username, password)
 1  officer ← find by username
 2  hash ← officer ? officer.passwordHash : DUMMY_HASH      ▷ timing equalisation

The dummy hash at line 2 of the login procedure is the whole of the timing defence. Without it, an unknown username returns in microseconds while a known one takes the 250 ms a cost-12 bcrypt comparison requires, and the difference is a usable oracle for enumerating accounts. With it, both paths perform one comparison and return the same body.

7.1 Introduction to Testing

A system that claims a security property is worth exactly what its evidence for that property is worth. This chapter therefore does not describe testing as a phase that followed construction; it describes the evidence collected, the technique that produced each item of evidence, and the defects that the process found.

The strategy had three layers. Automated integration tests exercised the HTTP surface against a real PostgreSQL database, because every guarantee this project claims — the unique index, the partial index, the transaction, the enum, the foreign key — is a database behaviour and would not be tested by a mock. Manual system tests walked each role through its workflow in a browser, because several requirements concern what a user is shown. Adversarial tests attempted the specific attacks the design claims to prevent, because a control that has never been attacked is an assumption rather than a control.

7.6.1 The Two Findings That Matter

A20 — the results endpoint is under-guarded. The route GET /simulator/elections/:id/results requires authentication but declares no role. Any authenticated caller, including a voter, can read the aggregate results of a closed election. The exposure is bounded — results are only available after closure, and they are aggregates that contain no voter and no ballot reference — but the route is inconsistent with every other route in the system, all of which name their roles explicitly. It is recorded as defect D-3 and as the first item of future work.

A4 — the choice of 404 over 403 is deliberate. When a voter requests another voter’s record, the API returns 404 rather than 403. A 403 would confirm that the identifier exists; a 404 reveals nothing. This is not an oversight in error design and it is asserted by a test, so that a future refactor towards “more correct” status codes does not silently re-open the enumeration channel.

7.6.2 What the Security Tests Do Not Establish

It is important to state the boundary of the evidence. The tests establish that the application’s own controls behave as specified. They do not establish that the system is secure against an attacker with database access, because no system with a single symmetric key and no hardware isolation can be. An attacker who can read the SubmittedBallot table and also read the environment can decrypt every ballot. What the design does achieve is that such an attacker must hold both the database and the key, and that the same attacker cannot use the database alone to learn which voter cast which ballot, because the link does not exist there. That is a meaningful reduction in exposure, and it is a different claim from “the ballot is secret”, which is why Section 8.3 states the limitation plainly.

CONCLUSION

8.1 Conclusion

This project set out to answer a narrow question: if a voter is allowed to vote somewhere other than their registered polling centre, what stops the remote act from changing the ballot they receive? The answer developed here is that nothing in the application has to stop it, because the structure does not permit it. A remote polling assignment names a centre and an election. It does not name a constituency, and no field exists in which one could be placed. The ballot is generated from a voter record that the remote workflow never writes. The choice is stored without a voter column, so the fact that a vote was cast and the fact of what was chosen live in two tables that share nothing but an election identifier.

The contribution is therefore not a new cryptographic protocol. Nothing in the sealing scheme is novel; AES-256-GCM with associated data is a standard construction, and the project uses it exactly as specified. The contribution is a demonstration that the organisational rule at the heart of remote voting can be enforced by data structure, and that the enforcement survives the ordinary pressures of implementation — the fourth defect in the register, D-12, is the project almost failing that test during its own design review, when a constituency column on the assignment looked like a reasonable convenience.

The simulator is complete within its scope. Five roles authenticate, a voter applies for a remote centre, an officer reviews and decides, an approved voter receives the ballot of their registered constituency at a different location, the ballot is sealed, the request is consumed, the election closes, reconciliation reports no discrepancy, and results are attributable to the correct constituency. Forty-nine automated cases and twenty adversarial attempts record that behaviour, along with ten defects found and fixed and two left open with reasons.

8.2 Achievements

The achievements below are stated in terms of what exists and can be inspected, not in terms of effort.

A working system, not a prototype of screens. All thirty-four documented routes are implemented and reachable, and every screen in Chapter 6 renders live data from the API. Invariants that a reviewer can attack. The unusual property of this project is that its central claims are falsifiable by anyone with a database client. A reviewer can attempt a second ballot, attempt an illegal transition, inspect the ballot table for a voter column and inspect the audit trail for a candidate identifier. A documented boundary between two data stores. The separation of identity from choice is drawn in the schema, in the data flow diagrams, in the class model and in the entity-relationship model, and the same absence appears in all four.

An honest test record. Forty-nine cases, five journeys, twenty adversarial attempts, four recovery scenarios and thirteen defects, including two that remain open and one accepted limitation.

8.2.1 What Was Learned

Three lessons are worth recording, because each cost time and each changed the implementation.

A check that runs in application code is not a guarantee. The first submission path read the voting status, decided there was none, and then wrote two rows. It passed every sequential test. The concurrency case showed that two requests could both read “not voted” and both write. The fix was not a lock in the service but a constraint in the database plus a guarded update, and the lesson generalises: if two requests can arrive together, the decision must be made by the store.

8.3.3 What the Evidence Does Not Establish

The system is not secure against an attacker holding both the database and the key. With both, every ballot can be decrypted, and the separation of the two tables provides no protection. The design reduces exposure by requiring two distinct compromises rather than one; it does not eliminate the possibility. A production system would place the key in hardware, split it between authorities, or use a threshold scheme — all of which are outside this project’s scope and none of which the report claims.

The system has not been audited. The cryptographic choices follow NIST SP 800-38D and the operational rules in the project’s threat model, but no independent review of the implementation has taken place. The test suite demonstrates that the code does what the author intended, which is not the same as demonstrating that what the author intended is correct.

The performance figures describe one user. Section 7.7 reports sequential timings on a development machine. Nothing in this report supports a claim about behaviour under concurrent load, and the in-process rate limiter means such a claim could not be made without a shared store first.

The usability evidence is five participants. Section 7.8 reports four tasks performed by five people, one of whom was the project guide. That is enough to find an obvious misunderstanding, which it did, and not enough to support a claim of usability.

8.4.2 Medium-Term

Threshold decryption. Split the ballot key between the election administrator, the auditor and an independent authority, so that counting requires two of three. This is the single change that would most improve the security story, because it removes the “one key opens everything” property that Section 8.3.3 identifies as the main weakness. 165

Verifiable receipts. A voter currently receives an opaque reference that proves nothing. A receipt that commits to the sealed ballot — for instance a hash of the reference, election and ciphertext — would let a voter confirm after counting that their ballot was included, without revealing what it contained. This is the property that end-to-end verifiable systems such as Helios and ElectionGuard provide, and it is the most commonly requested feature in any discussion of remote voting.

Append-only audit with chaining. Each audit record would carry a hash of its predecessor, so that a deleted or altered record breaks the chain. The current trail is append-only by convention; chaining would make tampering detectable rather than merely prohibited.

8.4.3 Long-Term

A real identity integration. Replacing the simulated voter number with an authenticated assertion from an electoral authority is the change that would turn a simulator into a candidate system, and it is also the change that would require the legal, operational and privacy work that this project deliberately excludes.

Accessibility conformance. The interface has not been tested with a screen reader. Conformance to WCAG 2.2 at level AA would be a requirement for any public deployment and would change the ballot screen substantially.

Multi-election operation. The current design assumes a single open election, enforced by findOpenElection. Supporting several concurrent elections would require the election to be chosen explicitly in every voter-facing route, which is a change to the API surface rather than to the schema.

An independent security review. Before any use beyond demonstration, the sealing scheme, the key handling and the audit design should be reviewed by someone other than their author. This is listed last because it is the most important.

8.5 Social Impact

Remote voting is not a neutral technical convenience. It changes who can vote, and it changes what a citizen must trust. A report that described only the engineering would be incomplete, so this section states the social case and the social risks in the same place.

8.5.1 The Case For

Migrant and seasonal workers. India’s internal migration is large and its election-day travel burden falls hardest on the poorest. A worker who cannot afford to return to a home constituency for a day effectively loses the franchise. A remote centre within reach addresses this without changing the constituency arithmetic.

Students and posted employees. The same argument applies to anyone resident elsewhere during a poll, including students in hostels and public servants under posting.

Voters with reduced mobility, and older voters. A nearer centre reduces the journey, and in a fuller implementation it could reduce the assistance required at the polling station — assistance which is itself a source of coercion risk.

Election-day disruption. Where a poll is disrupted by weather, unrest or a technical failure at one centre, a voter assigned elsewhere has an alternative that does not require the poll to be re-run.

8.5.2 The Case For Caution

The same feature carries risks that a simulator does not experience. Coercion moves into the home. A voter who can vote from a nearby centre, and in a fuller system from anywhere, can be accompanied, observed or instructed in a way that a supervised polling station makes difficult. Family voting is a documented problem in systems that allow voting outside a booth. Trust shifts to the operator. A paper ballot can be recounted by hand by anyone; a sealed electronic ballot can be counted only by whoever holds the key, which is why Section 8.4.2 puts threshold decryption and verifiable receipts ahead of any other enhancement.

The design in this project reduces one specific risk — the risk that the remote act changes the ballot — and is silent on the others. Being explicit about that silence is more useful than claiming a general improvement to electoral integrity.

167

8.5.3 Ethical Position Taken

Three commitments shaped the project. No claim beyond the evidence. The report does not describe the system as secure, verifiable or auditable without qualification; it describes what is enforced, what is tested and what is not. No real data. Every voter, officer and candidate is fictional, and no real voter roll, address or identifier was used at any stage. No concealed limitation. The two open defects, the accepted limitation and the three evidentiary gaps are recorded in the same document as the achievements, because a report that hid them would be less useful to the next person who builds on it.

8.6 Final Remarks

The project began with a sentence from a specification: a remote polling centre changes where a voter votes, never their registered constituency or ballot. That sentence could have been implemented as a validation rule in a service, tested with a case that passes a wrong constituency and expects a refusal, and documented as a requirement satisfied. It would have taken an afternoon.

What this project did instead was to ask what would have to be true for the sentence to hold without being checked. The answer was a set of absences: no constituency on the assignment, no voter on the ballot, no centre in the ballot generator’s signature, and no relation between the two tables. Absences are harder to review than assertions, because there is nothing to point at. They are also harder to break by accident, which is why they were worth the effort.

The work also produced evidence that the effort was needed. In its own design review the project nearly added the constituency column that would have undone the rule, and it did so for the ordinary reason that the approval code would have been shorter. That near-miss — recorded as D-12 — is the most honest thing in this report, because it shows that the rule is not obvious and that a careful designer can drift towards violating it while solving a different problem.

Two limitations remain open, and the report says so. The results route is under-guarded, which is a one-line fix that the project did not make before writing this page. The audit record is written after the commit, which prefers consistency of state to completeness of the log. Neither is difficult to repair; both are recorded because a limitation that is written down is a limitation that someone will fix, and one that is omitted is one that will be discovered by an examiner instead.

As a college project, the deliverable is a working application, a design that can be inspected, a test record that can be attacked, and a document that states its own boundaries. As a contribution to the discussion of remote voting, the deliverable is a small demonstration of a general idea: that the organisational rule at the centre of an electoral process can be made structural, and that making it structural is a different and stronger thing than making it a requirement.

export const TRANSITIONS: Record<Status, readonly Status[]> = {
  PENDING:      ['UNDER_REVIEW', 'WITHDRAWN', 'EXPIRED'],
  UNDER_REVIEW: ['APPROVED', 'REJECTED', 'WITHDRAWN', 'PENDING', 'EXPIRED'],

  WITHDRAWN:    [],
  USED:         [],
  EXPIRED:      [],
} as const;

export function assertLegal(from: Status, to: Status): void {
  if (!TRANSITIONS[from].includes(to))

C.3 The Verification and Counting Split

// Returns a boolean. Exposes no plaintext to any caller.
export function verifyBallot(sealed: Sealed): boolean {
  try {
    const decipher = crypto.createDecipheriv('aes-256-gcm', key, sealed.nonce);
    decipher.setAAD(Buffer.from(AAD(sealed.ref, sealed.electionId, sealed.constituencyId)));
    decipher.setAuthTag(sealed.authTag);
    decipher.update(sealed.ciphertext);
    decipher.final();
    return true;
  } catch { return false; }
}

// Returns the plaintext. Called only from the simulator, only after closure.
export function openBallotForCounting(sealed: Sealed): string {
  const decipher = crypto.createDecipheriv('aes-256-gcm', key, sealed.nonce);
  decipher.setAAD(Buffer.from(AAD(sealed.ref, sealed.electionId, sealed.constituencyId)));
  decipher.setAuthTag(sealed.authTag);
  return Buffer.concat([decipher.update(sealed.ciphertext), decipher.final()])
    .toString('utf8');
}

The split is the point. Two functions, two return types, one caller each. A path that must not disclose a choice is given the function that cannot.
