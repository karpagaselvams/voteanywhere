Validating configuration at start-up rather than at first use is a small decision with a large effect. A missing encryption key discovered when the first voter submits a ballot is an incident; discovered when the process starts, it is a line in the terminal. The configuration module therefore parses the environment with a Zod schema and throws before the HTTP server binds a port.

5.2.3 Client-Side Requirements

The client needs nothing beyond a browser. The built frontend is a static bundle of roughly 300 kB before compression, and the largest view renders a table of at most a few dozen rows. A device with 2 GB of memory is sufficient. No camera, no fingerprint reader, no smart card and no trusted platform module is required, and this is a design consequence rather than a limitation: the system simulates identity verification rather than performing it, so the hardware that would carry the trust is deliberately out of scope.

5.3 Languages Used

Four languages appear in the repository: TypeScript for all application code, SQL inside migrations, CSS through Tailwind, and Markdown for documentation. Each is used where it is strongest.

5.3.1 TypeScript

TypeScript 5.7 is used for the backend, the frontend and the tests. The decisive reason is not developer convenience but the class of error it removes. In a system whose central property is a boundary that must not be crossed, a compiler that knows the shape of a SubmittedBallot and refuses to accept a voter identifier in the function that creates one is worth more than any amount of prose. Three specific uses of the type system matter:

Discriminated session types. The session payload is a union of an officer session, a voter session and a system actor, distinguished by actorType. A handler that reads officerId must first narrow to the officer variant, so a voter session cannot be read as an officer session by accident.

Literal union statuses. The seven request statuses are a union of string literals generated from the Prisma enum. The transition table is typed as a record from every status to an array of statuses, so an illegal target cannot be written without a type error.

Function signatures as policy. generateBallot(voter: Voter) and sealChoice(choice: string, ballotReference: string, electionId: string, constituencyId: string) are both signatures in which the Core Rule is encoded. The first takes a whole Voter object rather than a loose constituency identifier, which is deliberate: a caller cannot supply a constituency at all, even by mistake. Widening either signature is a visible act in a code review.

5.3.2 SQL

SQL appears in two places. Migrations are generated by Prisma and reviewed, with one statement hand-written: the partial unique index. Queries are written in Prisma’s query language rather than raw SQL, except for aggregate counts, which use Prisma’s groupBy and count. No string concatenation reaches the database driver, so the injection class of defect is absent by construction rather than by sanitisation.

5.3.3 CSS and Tailwind

Tailwind CSS 4 is used through its Vite plug-in. Utility classes are preferred over component stylesheets because the interface is small and the design tokens are few: a slate-and-indigo palette, a five-step type scale and a single spacing rhythm. Where a repeated pattern exists — a card, a badge, a stepper — it is a React component with a fixed set of classes rather than a stylesheet rule, so the repetition is expressed in one place in TypeScript.

Two details of this sequence are worth noting. The seed is idempotent, so step 6 can be repeated without duplicating rows; it uses upserts keyed on the natural codes. And the tests run against the same database as development, in band, which is acceptable because the suites are written to tolerate the seeded rows rather than to assume an empty database. A separate test database would be the more rigorous arrangement and is listed as a limitation in Section 8.3.

5.5.4 Configuration Management

Configuration is separated into three classes, and only the first is committed.

Committed defaults. .env.example lists every variable with a comment explaining how to produce a valid value. It contains no secret: the encryption key entry is the string replace_with_64_hexadecimal_characters, which fails validation loudly if used unchanged, and the seed password entry is similarly a placeholder.

Local values. .env is ignored by Git. It holds the developer’s own key, secret and database password.

Deployment values. Injected by the platform. The application reads only from process.env, so no code change is required between environments.

The validation schema is the enforcement point. It declares DATABASE_URL as a non-empty string, JWT_SECRET as at least 32 characters, and BALLOT_ENCRYPTION_KEY as exactly 64 hexadecimal characters. A deployment with a 63-character key does not start, which is the correct behaviour: a shorter key would be silently padded or truncated by the cipher and would produce a system that appears to work.

5.5.5 Version Control Practice

Two branches are used: main, which is always in a state where npm test passes, and short-lived feature branches. Each migration is committed together with the schema change that produced it, so that the migration history and the schema history are the same history. The repository root carries an AGENTS.md and a GLOSSARY.md because the project was developed with AI assistance and the invariants had to be stated once, in a file the assistant reads, rather than repeated in every prompt. Section 8.2 discusses that practice and what it cost.
