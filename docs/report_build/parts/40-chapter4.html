CHAPTER 4
SYSTEM DESIGN

4.1 Design Overview

Design is where a requirement becomes a structure. The requirements in Section 3.6 say that the correct ballot must be served and that secrecy must survive the remote act; this chapter says how, in terms of modules, data flows, classes and tables. It is the longest chapter of the report because it carries the argument the project is making.

4.1.1 Design Principles

Six principles governed every structural decision. They are stated first because each later choice can be traced to one of them.

P1 — Make the invariant unrepresentable, not merely checked. If the wrong value cannot be expressed, no check is required. This principle explains why generateBallot takes a Voter, why the assignment model has no constituency field, and why the choice table has no voter column.

P2 — Put consistency where concurrency happens. A check in application code is correct only until two requests arrive together. Anything that must be true across concurrent writers belongs in the database: a unique constraint, a partial index, a foreign key or a transaction.

P3 — One legal path per state change. Rather than scattering conditionals, every request transition passes through a single table and a single guard. Adding an illegal transition then requires editing the table, which is a visible act rather than an accidental omission.

P4 — Deny by default. Authorization is an explicit allow-list per route. A role that is not named has no access, so adding a role later grants it nothing by default.

P5 — Separate the layers by responsibility, not by ceremony. Routes parse and respond, services decide, repositories persist. There is no Prisma call in a service and no HTTP concern in a repository. The boundary is enforced by review rather than by a framework, and the codebase is small enough for that to work.

P6 — The schema is the documentation of last resort. Comments go out of date; constraints do not. Every model in schema.prisma carries a doc comment naming the invariant it protects, so that a reader who opens one file understands the design.

4.2 System Architecture

The application follows a three-tier layered architecture deployed as a modular monolith. That phrase contains two decisions that should be separated: the layering, which is about responsibility, and the monolith, which is about deployment.

4.2.1 The Three Tiers

Presentation tier. A React 19 single-page application, written in TypeScript and built by Vite. It holds no business rule that matters. It validates forms for the convenience of the user, guards routes so that a voter does not see officer screens, and renders what the API returns. Every one of these behaviours is a courtesy; the server does not rely on any of them.

Application tier. One Express 4 process, written in TypeScript, containing nine domain modules. Each module has a router that declares paths and middleware, a service that holds the decisions, a repository that holds the queries and, where input arrives, a Zod schema that validates it at the edge. Cross-cutting concerns — authentication, authorization, validation, rate limiting and error translation — are middleware, so they appear in the route declaration rather than inside the logic.

Data tier. PostgreSQL 16 through Prisma 6. This tier is where the invariants that must survive concurrency actually live. The application asks the database to enforce them and translates the resulting errors into domain errors; it does not re-implement them.

4.2.2 Why a Modular Monolith

A microservice architecture was considered and rejected. The argument for rejection is not that microservices are bad; it is that they solve problems this project does not have while creating problems it would have to solve.

The decisive consideration is transactional integrity. The approval of a remote polling request and the creation of the resulting assignment must both happen or neither; a distributed transaction would introduce a failure mode in which a voter is approved but holds no assignment, which is exactly the state the design exists to prevent. Keeping both writes in one database makes that state unrepresentable, which is principle P1.

Two details in this chain are worth naming. First, authenticate performs two checks: the JWT signature, which is cheap and stateless, and then a database lookup of the session row, which is neither. The second check is what makes revocation immediate, and it is the reason the system can promise that a deleted session stops working at once rather than in two hours. Second, validate writes the parsed value back onto the request, so that downstream code receives typed data. A service therefore never trims, coerces or re-parses; if a value reaches a service it has already been accepted by the schema.

4.2.5 Deployment View

During development, three processes exist. PostgreSQL 16 runs in a Docker container with a named volume and a health check. The backend runs on the host under a watch-mode TypeScript runner, listening on port 4000. The frontend runs on the host under the Vite development server on port 5173, with a proxy that forwards /api to port 4000. The proxy is not a convenience: it means the browser sees one origin, so no cross-origin configuration is needed locally and the production topology — a reverse proxy serving the built frontend and forwarding the API path — is the same shape.

4.5.2 Rationale for the Class Structure

Five features of the class structure deserve comment, because each is a decision rather than an accident of modelling.

No inheritance is used. A conventional object model might introduce a base Actor class with Officer and Voter as subclasses. This design does not, and the reason is concrete: the two actors have entirely different authentication mechanisms, different session semantics and different lifecycles, and the only thing they share is that both produce a session. That shared fact is represented in Session, which carries an actorType discriminator and two optional foreign keys. The result is a shallower hierarchy and a simpler query, at the cost of two nullable columns — a trade judged worthwhile because the nullability documents precisely which combinations are legal.

ElectionConstituency is an association class with a primary key, not a bare join table. It carries a composite primary key on the pair, which means the pair can be referenced as a whole. That capability is used: Candidate has a composite foreign key to (electionId, constituencyId), and the effect is that a candidate cannot be created for a constituency that is not part of the election. The constraint is expressed once, in the schema, and holds for every insert regardless of which code path performs it.

The assignment has no constituency attribute. This is the single most important absence in the diagram. An approved assignment tells a voter which centre they may attend and which election it concerns. It says nothing about which ballot they will receive, because that is determined by the voter record alone. A modeller who added constituencyId here for convenience would make the Core Rule a runtime check rather than a structural fact.

SubmittedBallot has no voter attribute. It has a ballot reference, an election, a constituency and three cryptographic fields. There is no voter identifier and no relation by which one could be reached. The diagram shows the class floating free of the identity side, which is the visual statement of the secrecy boundary.

AuditRecord references entities by string, not by foreign key. This is intentional. A foreign key would create a referential constraint that would prevent the audit trail from outliving the record it describes, and it would also invite joins that reconstruct the very relationships the audit design avoids. The entityRef is an opaque string: a voter identifier for a voter action, a request identifier with its transition for a state change, a ballot reference with a system actor for a submission. The audit trail therefore records facts about operations without becoming a graph of the system.

4.6.3 The Core Rule in the Schema

The Core Rule states that a remote polling centre changes where a voter votes and never changes the registered constituency or the ballot received. Three schema facts enforce it, and none of them is a comment.

Fact one. Voter.registeredConstituencyId is a non-nullable foreign key, and it is the only place the association between a voter and a constituency is stored as an enrolment. No other table records an alternative.

Fact two. RemotePollingAssignment contains pollingCentreId and contains no constituency column. To discover the ballot for an assigned voter, a query must go through Voter.registeredConstituencyId, because that is the only path the schema offers.

Fact three. SubmittedBallot.constituencyId is written from voter.registeredConstituencyId at submission time, and the service that writes it never receives a constituency as input. Reconciliation then compares counts grouped by the same value, so a ballot cast at a remote centre is counted towards the voter’s own constituency rather than the centre’s.

The last two rows are the point. A voter standing in Madurai receives the Chennai South ballot and their ballot is counted in Chennai South. The reconciliation report attributes the ballot to Chennai South because both sides of the comparison are keyed by the registered constituency. Nothing in the journey moved the voter’s enrolment.

Now consider what a developer would have to do to break the rule. They could add a constituencyId to the assignment model — a visible schema change requiring a migration. They could change the signature of generateBallot to accept a constituency — a visible change to a public function, which the regression test in Section 7.4 names explicitly. They could write a query that joins the assignment to the polling centre and takes the centre’s constituency — which would require ignoring the fact that the ballot service never reads the assignment for anything except the centre’s display name. None of these is impossible, but each is a deliberate act that a reviewer would notice, which is the most a design can achieve.

4.6.5 Cardinality Under the Secrecy Boundary

The secrecy boundary produces an unusual situation in relational terms: two tables that are conceptually related by a single real-world event but have no join path. The relation between them exists only as a fact outside the database — the same person performed both writes in the same transaction.

This is not a normalisation defect. It is the deliberate removal of a functional dependency that the system must not be able to compute. A database theorist would say that the relation “which voter cast which ballot” is held in the operator’s memory and in the wall-clock ordering of transactions, and deliberately not in the schema. Anything that could reconstruct it — a shared nonce, a timestamp precise enough to correlate, a sequence number — has been avoided. The ballot reference is random and non-sequential precisely so that it orders nothing.

4.7.6 Invariants Held After Every Transition

Five invariants hold in every reachable state. They are stated so that they can be tested, and Section 7.4 records the tests that check them.

  1. INV-1. A request in APPROVED or USED has exactly one assignment; a request in any other state has none.
  2. INV-2. A voter has at most one request in PENDING or UNDER_REVIEW per election.
  3. INV-3. A request in REJECTED has a non-empty review note.
  4. INV-4. No transition writes to Voter.registeredConstituencyId.
  5. INV-5. Every state change has a corresponding audit record.

INV-1 is enforced by the transaction and by the unique constraint on requestId. INV-2 is enforced by the partial unique index. INV-3 is enforced by the validation schema and a service guard. INV-4 is enforced by the absence of any such write in any repository; it is a property of the code rather than of the schema, which is why it is also the subject of a test. INV-5 is enforced by convention at every call site, and it is the invariant most vulnerable to a future developer adding a transition without an audit call — a risk noted in Section 8.3.

4.7.7 Election Lifecycle

The election has a simpler lifecycle with a stricter rule: it moves forward only, and only once per step.

Figure 4.10: Election lifecycle and its guards

The lifecycle interacts with the request machine in four places. Requests may be submitted only in CONFIGURED; this is deliberate, because a voter who applies after the poll has opened is applying to vote in a poll already under way, and the administration cannot review in time. Ballots may be generated and submitted only in ACTIVE. Approvals are refused once the election is CLOSED, even if the request was claimed before closure, because a permission granted after the poll has ended is worthless. And closure itself is the system transition that expires every still-open request, so the batch operation is recorded as a series of system-actor audit records rather than as a silent update.

4.7.9 The Partial Unique Index

One constraint deserves separate treatment because it is the only piece of the schema that Prisma cannot express. The rule is: a voter may hold at most one active request per election, where active means PENDING or UNDER_REVIEW. A voter may hold any number of historical requests in terminal states, because a rejected or withdrawn application must not prevent a new one.

A plain unique index on (voterId, electionId) would be wrong, because it would also forbid a second request after the first was rejected. A check in application code would be wrong, because two concurrent submissions could both pass it. The correct instrument is a partial unique index, which applies uniqueness only to rows matching a predicate.

-- backend/prisma/migrations/20261030175226_init/migration.sql
-- At most one active (PENDING or UNDER_REVIEW) remote polling request per
-- voter per election. Prisma cannot express partial indexes, so this is
-- hand-written; the constraint name must never reach a response body.
CREATE UNIQUE INDEX "RemotePollingRequest_one_active_per_voter_election"
ON "RemotePollingRequest" ("voterId", "electionId")
WHERE "status" IN ('PENDING', 'UNDER_REVIEW');

Three consequences follow. First, the database now refuses a second active request even if the service layer is bypassed, which is the property a constraint is for. Second, the service must translate the resulting error code, P2002, into a domain error, because a raw constraint violation must never reach a client. Third, the index is invisible to Prisma’s schema-diffing, so a future developer who regenerates the schema will not produce this index and must be told about it — which is why the index carries a comment in the migration and is named in Appendix A.

4.8 Input and Output Design

Input and output design governs what a user is asked for, in what order, and what they are shown in return. Two rules were applied throughout. Ask only for what the server needs and cannot derive, and show the derived value back so that the user can see that the system understood.

4.8.1 Input Design Principles

Derive rather than ask. The voter is never asked for their voter identifier when submitting a request or a ballot; it comes from the session. The voter is never asked for their constituency; it is shown, not requested. The officer is never asked which election they are acting on when the concept of a current election applies.

Constrain at the edge. Every endpoint that accepts a body or a query parameter declares a Zod schema. The schema runs before the handler, so a malformed identifier is refused with a 400 before any database work happens. The schemas are small and literal: a UUID, a bounded string, an enum member.

Label the consequence. The centre-selection list shows each centre with its constituency, so that a voter can see that the centre they are choosing is outside their own constituency before they submit. The interface does not hide the rule; it explains it at the moment of choice.

Refuse with a reason. A refusal that says “invalid request” teaches nothing. The domain errors in this system carry a sentence: choose a polling centre outside your registered constituency — your home centre is the default is more useful than 422, and it is what the code actually returns.

4.8.3 Output Design Principles

Return the smallest sufficient shape. A ballot response contains the election, the constituency, the candidates and, if one exists, the assignment. It does not contain the voter identifier, because the caller already knows who they are and nothing downstream needs it. A submission response contains an opaque reference and a timestamp, and nothing else — in particular it does not echo the choice back.

Make the state visible. Every request shape carries its status as an enum value, and the interface renders it as a badge with a colour and a word. A voter should never have to infer their position in the workflow.

Explain refusals. Domain errors carry a sentence that names the remedy where a remedy exists.

Never leak structure. The error handler converts an unexpected failure into a fixed 500 body and logs the name only. A Prisma error, a constraint name or a stack trace never reaches a client.

4.8.9 Design Summary

Chapter 4 has established eight things. An architecture of three tiers deployed as a modular monolith, chosen for transactional integrity. A request path in which authentication, authorization, validation and error translation are all middleware, and in which revocation is immediate because the session row is re-read on every request. Three levels of data flow, of which the significant feature is a non-arrow between the identity store and the choice store. A use case model with five actors and a realisation matrix that maps every use case to a route and a method. A class model in which the two most important facts are absences: the assignment has no constituency and the ballot has no voter. An entity-relationship model with fifteen relationship lines, of which one is deliberately missing. A database design in which four constraints carry the invariants that matter, including one hand-written partial index. And an input-output design in which the ballot screen explains the Core Rule to the voter at the moment it matters.

The design decisions that a reader should carry into Chapter 5 are these:

  • The Core Rule is enforced by a function signature and by two absences in the schema, not by a validation check.
  • Duplicate ballots are prevented by a unique constraint evaluated inside a transaction, not by a read-then-write.
  • The transition table is the single source of legality for request state changes.
  • The assignment and the approval are written in one transaction because an approved request without an assignment is an incoherent state.
  • The secrecy boundary is a schema boundary: two tables, no key, no relation.
  • Authorization is an explicit allow-list on every route, so the default is refusal.
  • Ballot verification returns a boolean and counting is a separate function, so the verification path has no type-level way to disclose a choice.

Chapter 5 turns to the technology stack that implements this design, and Chapter 6 to the implementation itself — the modules, the algorithms, the pseudocode and the code sketches.
