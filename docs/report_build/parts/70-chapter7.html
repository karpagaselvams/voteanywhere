CHAPTER 7
TESTING

7.1 Introduction to Testing

A system that claims a security property is worth exactly what its evidence for that property is worth. This chapter therefore does not describe testing as a phase that followed construction; it describes the evidence collected, the technique that produced each item of evidence, and the defects that the process found.

The strategy had three layers. Automated integration tests exercised the HTTP surface against a real PostgreSQL database, because every guarantee this project claims — the unique index, the partial index, the transaction, the enum, the foreign key — is a database behaviour and would not be tested by a mock. Manual system tests walked each role through its workflow in a browser, because several requirements concern what a user is shown. Adversarial tests attempted the specific attacks the design claims to prevent, because a control that has never been attacked is an assumption rather than a control.

Two decisions in this environment are worth defending. 7.3.1 The Concurrency Test in Detail

Objective O1 is the one that a naive implementation passes by accident and a concurrent one fails. The test issues several submissions for the same voter with Promise.all, so they arrive at the server together, and then asserts that exactly one response is a success and that the ballot table holds exactly one row for that election and constituency.

// illustrative form of the concurrency case
const results = await Promise.allSettled(
  Array.from({ length: 4 }, () =>
    request(app).post('/api/simulator/controlled-ballot/submit')
      .set('Authorization', `Bearer ${voterToken}`)
      .send({ candidateId })),
);
const ok = results.filter(r => r.status === 'fulfilled' && r.value.status === 201);
expect(ok).toHaveLength(1);
expect(await prisma.submittedBallot.count({ where: { electionId } })).toBe(1);

The test is meaningful only because the application does not serialise requests artificially. If it had used a process-wide lock, the test would pass while proving nothing about the database constraint; the design deliberately relies on the constraint, so the test asserts the constraint’s effect.

7.4.2 The Core Rule Test

This case is reproduced because it is the single most important assertion in the project. It creates a voter registered in one constituency, approves a remote request for a centre in another, generates the ballot and asserts that every candidate belongs to the registered constituency.

it('serves the registered constituency even when approved elsewhere', async () => {
  // voter registered in CHN-S, approved to attend MDU-C-01
  const res = await request(app)
    .get('/api/simulator/controlled-ballot')
    .set('Authorization', `Bearer ${voterToken}`);

  expect(res.status).toBe(200);
  expect(res.body.constituency.code).toBe('CHN-S');
  expect(res.body.remoteAssignment.pollingCentre.code).toBe('MDU-C-01');
  for (const candidate of res.body.candidates)
    expect(candidate.constituency.id).toBe(res.body.constituency.id);
});

The second assertion and the loop together state the Core Rule as an executable claim: the assignment points elsewhere while every candidate belongs to the voter’s own constituency. A future change that passed the centre into ballot generation would fail this case, which is the purpose of writing it this way.

7.5.2 ST-2 — Refusal of an Own-Constituency Centre

As VA-0001, a request was submitted for CHN-S-01, the voter’s own home centre. The interface refused with: choose a polling centre outside your registered constituency — your home centre is the default. No row was created. The same attempt through the API directly returned 422 with the same sentence, confirming that the interface message was the server’s message rather than a client-side check.

7.5.3 ST-3 — Verification at a Centre

As officer.polling, VA-0001 was looked up. The screen reported the registered constituency, the assignment to MDU-C-01 marked valid, and a ballot status of not yet submitted. After the ballot was submitted in ST-1, the same lookup reported the ballot as submitted, and the entitlement message changed accordingly. Nothing on the screen offered an action, and no request was written by the lookup.

7.5.4 ST-4 — Closure, Reconciliation and Results

As admin.asha, the election was closed. The open request in the database moved to EXPIRED and one audit record was written with the system actor. Reconciliation then returned a discrepancy of zero in both constituencies, and results attributed the single ballot to Chennai South even though it had been cast at a Madurai centre. An attempt to read reconciliation while the election was ACTIVE had earlier returned 409 with election is not closed.

7.5.5 ST-5 — Auditor Access

As auditor.dev, the audit trail was read with a filter on action. The record list showed the login, the submission, the claim, the approval, the submission of the ballot and the closure, each with an actor type and an entity reference. The auditor could not approve, claim or close anything; every such attempt returned 403.

7.6.1 The Two Findings That Matter

A20 — the results endpoint is under-guarded. The route GET /simulator/elections/:id/results requires authentication but declares no role. Any authenticated caller, including a voter, can read the aggregate results of a closed election. The exposure is bounded — results are only available after closure, and they are aggregates that contain no voter and no ballot reference — but the route is inconsistent with every other route in the system, all of which name their roles explicitly. It is recorded as defect D-3 and as the first item of future work.

A4 — the choice of 404 over 403 is deliberate. When a voter requests another voter’s record, the API returns 404 rather than 403. A 403 would confirm that the identifier exists; a 404 reveals nothing. This is not an oversight in error design and it is asserted by a test, so that a future refactor towards “more correct” status codes does not silently re-open the enumeration channel.

7.6.2 What the Security Tests Do Not Establish

It is important to state the boundary of the evidence. The tests establish that the application’s own controls behave as specified. They do not establish that the system is secure against an attacker with database access, because no system with a single symmetric key and no hardware isolation can be. An attacker who can read the SubmittedBallot table and also read the environment can decrypt every ballot. What the design does achieve is that such an attacker must hold both the database and the key, and that the same attacker cannot use the database alone to learn which voter cast which ballot, because the link does not exist there. That is a meaningful reduction in exposure, and it is a different claim from “the ballot is secret”, which is why Section 8.3 states the limitation plainly.

7.7 Performance Testing

No load generator was used. Timings were recorded with sequential requests against the seeded database on the development machine, which is enough to identify an order of magnitude and not enough to characterise the system under load. The results are reported with that caveat.

GET .../results30–60 msDecrypting every ballot

Table 7.9: Observed response times (development machine, sequential requests)

Two conclusions follow from these figures. First, authentication dominates: a login costs roughly twenty times a business request, which is the intended consequence of choosing a deliberately slow hash. Second, the cryptographic work is not a bottleneck; sealing and opening a ballot is cheaper than the database round trip that surrounds it. The figure that would matter at scale is the results endpoint, which decrypts every ballot in the election and therefore grows linearly with turnout; at the scale of this project, with a single ballot, it is invisible.

7.10 Recovery Testing

Four interruption scenarios were exercised. The purpose is to confirm that the transaction boundaries described in Chapter 6 mean what they claim.

#ScenarioOutcome
R1Backend process killed during the submission transactionOn restart, no ballot row and no consumed identity; the voter could vote again
R2PostgreSQL container stopped and restartedPrisma reconnected; the next request succeeded without a process restart
R3Duplicate submission attempted while the first was in flightOne committed, one refused; no partial state
R4Election closed while a request was being approvedClosure won; the approval was refused with 409 on the lifecycle guard

Table 7.13: Recovery scenarios

R1 is the scenario that justifies placing both writes in one transaction. Had the identity been marked outside the transaction, a killed process would have left a voter recorded as having voted with no ballot stored — a state from which the voter cannot recover without an administrator. R4 is the scenario that justifies checking the lifecycle inside the approval rather than only at the start of the request.

Against the six objectives, the outcome is as follows. O1 is met and demonstrated under concurrency. O2 is met, asserted by the Core Rule case and by the reconciliation of a ballot cast at a remote centre. O3 is met within the application’s own outputs; no response, log line or audit record was found to carry a choice, though the limitation stated in 7.6.2 applies to an attacker with database and key access. O4 is met for every route except the results route, which is defect D-3. O5 is met; the transition table refused every illegal attempt in the request and in the lifecycle. O6 is met; a revoked session failed on the next request.

What the testing does not establish should be repeated once more, because it is the honest boundary of the chapter. There is no frontend test suite, so a regression in a React component would be caught only by manual inspection. There is no load test, so the performance figures in Section 7.7 describe one user at a time. And there is no formal verification of the transition table, only an exhaustive table and a sample of negative cases. These three gaps are carried into Section 8.3 rather than left implied.
