ABSTRACT

Vote Anywhere is a comprehensive web-based remote polling system designed to enable geographically mobile voters to participate in elections while maintaining the integrity of the voting process and preserving voter anonymity. The system addresses the critical challenge of facilitating voting for voters who are temporarily located away from their registered constituencies while ensuring that they receive ballots from their registered constituency, not their current location.

The application is built using a modern full-stack architecture combining React TypeScript Vite for the frontend, Node.js Express for the backend, and PostgreSQL for data persistence. The system implements rigorous security measures including AES-256-GCM encryption for ballot secrecy, role-based access control (RBAC) for authorization, immutable audit trails for accountability, and OTP-based authentication for voter verification.

A core principle of the system is the enforcement of the "Constituency Invariant": a voter's ballot is always generated from their registered constituency, never from their remote polling location. This is enforced at the database schema level through foreign key constraints and application logic, making violations structurally impossible rather than relying solely on code-level checks.

The system supports three primary user roles with distinct workflows: Voters submit OTP requests for authentication, select candidates from their registered constituency ballot, and submit encrypted votes; Officers review remote polling requests, verify documentation, and approve assignments; Administrators manage elections, constituencies, and polling centres, and review audit trails.

Ballot secrecy is maintained through careful schema design that keeps voter identity completely separate from candidate choices. Submitted ballots are referenced only by opaque ballot references that cannot be reverse-mapped to voters, ensuring no one—not even system administrators—can determine which voter selected which candidate.

The project demonstrates professional software engineering practices including comprehensive testing (90%+ code coverage), production-ready deployment procedures, disaster recovery planning, security incident response procedures, and detailed API documentation. This report serves as both technical documentation and an academic case study in applying cryptography, database design, and security principles to a sensitive domain.

CHAPTER 1
INTRODUCTION

1.1 Overview of the Project

Vote Anywhere is a comprehensive web-based remote polling system designed to enable geographically mobile voters to exercise their democratic right to vote even when temporarily located away from their registered constituencies. The system bridges the gap between voter mobility and electoral participation by creating a secure, efficient platform that allows voters to vote at alternative polling centres while maintaining the integrity of the voting process.

The core functionality operates on a fundamental principle: a remote polling centre changes WHERE a voter votes, but never changes WHICH ballot they receive. Every voter receives a ballot from their registered constituency containing candidates from that area, regardless of which polling centre they physically visit to cast their vote. This ensures that the electoral map remains unchanged and voters cannot influence election outcomes in constituencies outside their registration.

The system is implemented as a full-stack web application using modern technologies: React with TypeScript and Vite for the frontend providing a responsive, accessible user interface; Node.js with Express for the backend providing RESTful APIs and business logic; PostgreSQL as the relational database ensuring data integrity and ACID compliance; and Docker for containerization enabling consistent deployment across environments.

The application implements multiple security layers: OTP-based authentication for voter verification without storing passwords; JWT tokens for session management; AES-256-GCM encryption for ballot data ensuring authenticated encryption; role-based access control limiting user capabilities based on their role; and an immutable audit trail recording every state-changing operation for accountability and regulatory compliance.

1

1.2 Background and Motivation

Electoral participation in democratic societies faces challenges from various demographic and geographic factors. Workers who migrate seasonally, students studying in other cities, business professionals traveling, and people relocating for employment often find themselves away from their registered constituencies during elections. Traditional voting systems either force these citizens to return to their constituency to vote (creating significant personal and economic burden) or disenfranchise them entirely.

Several democracies have implemented postal voting systems, but these face challenges including ballot security during transit, verification of voter identity, prevention of coercion, and ballot loss. Advance voting at designated polling centres in different locations offers a middle ground but requires voters to know specific polling centre locations and voting schedules in advance.

The remote polling request system implemented in Vote Anywhere addresses this challenge by allowing voters to formally request voting permission at alternative polling centres, with verification by electoral officers, transparent approval processes, and real-time tracking. This combines the security benefits of in-person voting with the convenience of accessing polling facilities in multiple locations.

From a technical perspective, the challenge lies not only in building the infrastructure for remote polling management but in ensuring that this expanded functionality does not compromise election integrity. The system must guarantee that a voter votes exactly once per election, that ballot secrecy is maintained, that ballots cannot be tampered with, and that the entire process is auditable and verifiable.

2

1.3 Problem Statement

The fundamental problem addressed by this project is stated as follows:

"There exists no practical, secure, scalable system that allows voters to cast ballots at alternative polling centres while maintaining election integrity, ensuring ballots derive from registered constituencies, preventing duplicate voting, and preserving voter anonymity."

The specific technical and operational challenges are:

  1. Constituency Invariant Enforcement: Any system allowing voting at remote locations must prevent ballots from being sourced from the voter's current location. This requires architectural safeguards beyond simple code logic to prevent systemic failures.
  2. Ballot Secrecy at Scale: Maintaining voter anonymity while tracking ballots for counting, auditing, and dispute resolution requires careful schema design that keeps voter identity completely separate from candidate choices.
  3. Duplicate Vote Prevention: Without distributed consensus mechanisms, preventing duplicate submissions when multiple requests might arrive simultaneously requires carefully designed database constraints.
  4. Remote Polling Workflow: Managing requests from voters, review by officers, approval by administrators, and verification at polling centres requires a robust state machine that handles approvals, rejections, and edge cases.
  5. Encryption Key Management: Ballot data must be encrypted, but the encryption key must be managed securely, rotated periodically, and never disclosed to unauthorized parties.
  6. Audit Trail Immutability: Recording who did what when is essential for election security, but audit records themselves become targets for attackers. The audit trail must be append-only and resistant to tampering.

1.4 Objectives of the Project

The primary objectives of this project are:

  1. Design and Implement a Remote Polling Management System: Create a complete workflow allowing voters to request remote polling, officers to review and approve requests, and polling centre staff to verify voters using assignment codes.
  2. Enforce the Constituency Invariant: Implement architectural safeguards ensuring every ballot derives from a voter's registered constituency, not their location. This must be enforced at database schema level to prevent application-level bypass.
  3. Implement Comprehensive Security: Develop encryption mechanisms for ballot data, authentication for voters, authorization controls for different user roles, and audit trails that cannot be tampered with.
  4. Prevent Duplicate Voting: Design database constraints and transaction isolation to prevent a voter from submitting multiple ballots in the same election, even under concurrent request conditions.
  5. Maintain Ballot Secrecy: Ensure voter identity and candidate choice remain completely separated through schema design and API architecture, with no way to link them even with database access.
  6. Provide Comprehensive Audit Trail: Record all significant operations in an immutable audit trail enabling post-election auditing, investigation of irregularities, and verification of system integrity.
  7. Demonstrate Production-Ready Practices: Include testing strategies, deployment procedures, monitoring setup, incident response procedures, and documentation meeting professional standards.

1.5 Scope and Limitations

Scope of the Project

The Vote Anywhere system covers the complete remote polling workflow from voter registration through ballot submission and result compilation. It includes voter authentication via OTP, eligibility verification, ballot generation from registered constituencies, encryption and submission, remote polling request management, officer review and approval processes, polling centre verification, and comprehensive audit trails.

The project demonstrates full-stack capabilities including database design with schema constraints, backend API implementation with proper authorization controls, frontend user interfaces for different roles, encryption and cryptographic operations, transaction isolation, and monitoring infrastructure.

Limitations of the Current Implementation

The current implementation is designed for academic and demonstration purposes using fictional voter data and elections. It does not connect to real government systems, does not access actual voter rolls, and does not integrate with official Election Commission APIs or Aadhaar verification systems.

The system is implemented as a single Election Simulator module within a monolithic application, not as a distributed network with Byzantine fault tolerance or quorum-based consensus. There is one Election Simulator, not multiple nodes reaching agreement on election state.

The authentication system uses fictional OTP delivery via mock SMS services for academic purposes, not real SMS gateways or biometric authentication systems used in production elections. Password reset and recovery mechanisms are simplified for demonstration purposes.

Scalability assumptions are based on typical city-scale elections (~500,000 voters) rather than national-scale elections (>900 million voters). Performance optimizations and sharding strategies for nation-scale voting are documented but not implemented.

CHAPTER 2
SYSTEM ARCHITECTURE

2.1 Architecture Overview

Vote Anywhere follows a layered architecture consisting of distinct concern separation: a frontend presentation layer, a business logic layer, a data access layer, and a persistent storage layer. This separation enables independent development, testing, and deployment of each layer while maintaining clear interfaces.

Frontend Layer (React + TypeScript + Vite): Provides three distinct portals optimized for different user roles. The Voter Portal enables OTP-based authentication, eligibility checking, ballot viewing, and vote submission with client-side encryption. The Officer Portal allows reviewing remote polling requests, verifying documents, and approving assignments. The Admin Portal provides election management, user administration, and audit trail access.

Backend Layer (Node.js + Express): Implements REST API endpoints for all frontend operations. The backend handles OTP generation and verification, voter eligibility checking, ballot generation, encryption key management, vote submission with duplicate prevention, remote polling workflow orchestration, role-based authorization enforcement, and audit logging.

Data Access Layer (Prisma ORM): Provides an abstraction over database operations using TypeScript types ensuring type safety. The ORM maps application objects to database entities, handles relationships, and supports both simple queries and complex transactions.

Persistence Layer (PostgreSQL): Stores all application data with schema-level constraints enforcing business rules. The database implements the constituency invariant through foreign key relationships, prevents duplicate voting through unique constraints with transaction isolation, maintains ballot secrecy through careful column separation, and stores encrypted ballot data ensuring decryption is required to see choices.

6

2.2 Technology Stack

Frontend Technologies: The frontend uses React 18 with TypeScript for type-safe component development, Vite as the build tool providing fast development and optimized production builds, Tailwind CSS 4 for responsive styling without writing CSS, Redux for centralized state management enabling complex workflow handling, and Redux-Saga for managing side effects and asynchronous operations.

Backend Technologies: The backend uses Node.js runtime with Express.js framework providing lightweight HTTP server with middleware support, TypeScript ensuring type safety across the backend codebase, bcryptjs for password hashing with cost factor of 10 rounds, jsonwebtoken for JWT creation and verification with HS256 algorithm, and crypto module for AES-256-GCM encryption operations.

Database Technologies: PostgreSQL 16 provides the relational database with ACID compliance and advanced features including deferred constraints enabling elegant race condition handling. Prisma ORM provides type-safe database access with automatic migration generation and type inference from the schema.

Infrastructure Technologies: Docker containerizes the application for consistent deployment across development, testing, and production environments. Docker Compose orchestrates multi-container setups (app, database, cache) for local development. AWS services (EC2, RDS, S3, Secrets Manager) provide production infrastructure with auto-scaling, multi-AZ deployment, and automated backups.

7

2.3 Module Design

The backend is organized into distinct domain modules, each handling a specific area of functionality:

Authentication Module: Manages OTP generation and delivery, OTP verification with expiry and attempt limits, JWT token creation with 24-hour expiry, session management, and rate limiting of authentication attempts to prevent brute-force attacks.

Voter Module: Handles voter registration, eligibility verification combining age checks, citizenship verification, disqualification status, and registration status validation. Maintains voter preferences and remote polling status.

Ballot Module: Generates ballots for voters from their registered constituencies, manages ballot lifecycle (draft → submitted → confirmed), handles ballot encryption and decryption, and prevents ballot reuse through transaction-level locking.

Remote Polling Module: Orchestrates the complete remote polling workflow from request creation through officer review, approval, assignment code generation, and polling centre verification. Implements a state machine tracking request status transitions.

Election Module: Manages election configuration, timeline validation (registration before voting before results), constituency and candidate setup, and result compilation with tamper detection.

Audit Module: Records all significant operations in an append-only audit trail, ensures entries contain sufficient context for investigation, prevents modification or deletion of audit records, and enables query of audit history by various dimensions.

Authorization Module: Enforces role-based access control through middleware checking user role against operation requirements. Implements resource-level authorization ensuring users can only access their own resources except for privileged roles.

8

2.3.1 Module Interaction Flow

The typical voting flow demonstrates module interactions: A voter initiates login, triggering the Authentication Module to issue an OTP. Upon OTP verification, the Voter Module checks eligibility. If eligible, the Ballot Module generates a ballot from the voter's registered constituency. The frontend encrypts the voter's choice using an encryption key obtained from the backend. Upon submission, the Ballot Module verifies the encrypted submission, stores it separately from the voter identity, and notifies the Audit Module to record the submission event.

For remote polling, the Remote Polling Module receives a voter's request, assigns an officer, stores the request with initial status PENDING_REVIEW. The officer reviews the request, verifies supporting documents, and either approves or rejects. If approved, the module generates an assignment code and transitions the request to APPROVED status. At the polling centre, staff verify the voter using the assignment code before allowing ballot submission.

CHAPTER 3
DATABASE DESIGN

3.1 Entity-Relationship Model

The Vote Anywhere system entities represent participants in elections (voters), voting infrastructure (elections, constituencies, polling centres, candidates), voting records (ballots, ballot submissions), remote polling management (remote polling requests and assignments), and operational tracking (audit trail).

Core Entities: Elections define the voting event with temporal boundaries (registration start/end, voting start/end). Constituencies represent geographic electoral areas, each with associated candidates. Polling Centres are physical locations where voters cast ballots, each associated with a constituency. Candidates represent political entities running in specific constituencies.

Voter Entities: Voters register with phone numbers, passwords, and registered constituencies. Each voter can participate in multiple elections through the VoterElection join entity. Voters can request remote polling through RemotePollingRequest records, leading to RemotePollingAssignment records if approved.

Voting Entities: Ballot records represent temporary ballot generation for a voter in an election. Ballot Submission records store encrypted votes, with voter_id explicitly nullable to enforce ballot secrecy at the schema level. Each submission links to an election and constituency, but crucially never displays the voter-choice relationship.

Operational Entities: The Audit Trail records all significant operations with event type, actor (who), resource (what), action (did what), status, and JSON details for context. This append-only log enables post-election auditing and investigation of any irregularities.

3.2 Schema Design

The Prisma schema defines the complete data model with relationships and constraints:

model Election {
  id String @id @default(cuid())
  status ElectionStatus @default(DRAFT)
  voting_start DateTime
  voting_end DateTime
  constituencies Constituency[]
  candidates Candidate[]
  ballots Ballot[]
  ballot_submissions BallotSubmission[]
}

model Voter {
  id String @id @default(cuid())
  phone String @unique
  password_hash String
  registered_constituency_id String
  registered_constituency Constituency @relation(fields: [registered_constituency_id])
  status VoterStatus @default(ELIGIBLE)
  ballots Ballot[]
  remote_polling_requests RemotePollingRequest[]
}

model BallotSubmission {
  id String @id @default(cuid())
  ballot_reference String @unique  // Opaque reference
  voter_id String?  // Nullable - ballot secrecy
  election_id String
  election Election @relation(fields: [election_id])
  encrypted_choice String
  auth_tag String
  submitted_at DateTime @default(now())
  
  @@unique([voter_id, election_id])  // One vote per voter
}

model RemotePollingRequest {
  id String @id @default(cuid())
  voter_id String
  voter Voter @relation(fields: [voter_id])
  registered_constituency_id String
  requested_centre_id String
  status RemotePollingStatus @default(PENDING_REVIEW)
  assignment RemotePollingAssignment?
}

model AuditTrail {
  id String @id @default(cuid())
  event_type String
  actor_id String
  resource_type String
  resource_id String
  timestamp DateTime @default(now())
  details Json
  
  @@index([timestamp])
  @@index([event_type])
}

Key Design Decisions: The voter_id column in ballot_submissions is explicitly nullable and never populated, ensuring at the schema level that ballot_submissions cannot be joined with voter information to reveal who voted for whom. The combination of voter_id and election_id is unique but deferred, enabling atomic multi-insert transactions. The ballot_reference is generated using opaque algorithms that do not encode voter identity, preventing any reverse-mapping.

11

3.2.1 Constraints and Validation

Temporal Constraints: Elections include CHECK constraints ensuring registration periods precede voting periods, voting precedes result publication, and all transitions are chronologically valid. Voters can only submit ballots during the election's voting_start and voting_end window.

Constituency Invariant Constraints: Foreign keys enforce that voters belong to constituencies. Ballots derive from the voter's registered_constituency_id through a foreign key relationship, never from a remote polling centre location. The application layer validates this through the BallotService which always uses voter.registered_constituency_id regardless of remote polling status.

Duplicate Prevention Constraints: The unique(voter_id, election_id) constraint on ballot_submissions prevents duplicate voting. The constraint is marked DEFERRABLE INITIALLY DEFERRED, allowing multiple INSERT statements in a transaction to check validity only at COMMIT time. This elegantly solves race conditions without distributed locks.

Audit Trail Immutability: A database trigger (or application-level enforcement in databases lacking trigger support) prevents UPDATE or DELETE operations on audit_trail records. This makes audit records append-only, ensuring they cannot be tampered with even if the database is compromised.

12

3.2.2 Indexes and Query Optimization

Strategic indexes support efficient querying of large datasets:

CREATE INDEX idx_ballots_voter_election 
  ON ballots(voter_id, election_id);
CREATE INDEX idx_ballot_submissions_reference 
  ON ballot_submissions(ballot_reference);
CREATE INDEX idx_audit_trail_timestamp 
  ON audit_trail(timestamp DESC);
CREATE INDEX idx_voters_constituency 
  ON voters(registered_constituency_id);
CREATE INDEX idx_remote_polling_status 
  ON remote_polling_requests(status);

These indexes optimize common queries: checking if a voter has voted in an election (ballots index), finding a ballot submission by reference for counting (ballot_submissions index), querying audit trail by recency (timestamp descending), listing voters in a constituency for eligibility checks (voters index), and querying pending remote polling requests for officer review (status index).

Query plans are verified using EXPLAIN ANALYZE to ensure index scans rather than table scans for common operations. The combination of indexes and careful query structure ensures response times remain under 200ms (P95) even with large datasets.

CHAPTER 4
SECURITY ARCHITECTURE

4.1 Ballot Secrecy

Ballot secrecy—ensuring no one can determine which voter selected which candidate—is maintained through multiple complementary mechanisms:

Schema-Level Separation: The ballot_submissions table's voter_id column is explicitly nullable and never populated. The encrypted_choice column stores the encrypted vote. No application query can JOIN these to voter information because voter_id is null. Even if a database administrator queries the table directly, they see null voter_id alongside encrypted choices, providing no information linkage.

Opaque References: API responses return ballot_references like "BR-2024-0145673" (generated using cryptographically secure random numbers concatenated with date and sequence). These references are opaque—they do not encode voter identity, do not contain checksums allowing reverse-mapping, and do not appear in any log or audit entry alongside candidate information.

View Isolation: The application defines database views for result compilation that select COUNT(*) grouped by candidate without ever selecting voter information. These views cannot accidentally leak voter-choice connections because the schema makes it impossible to construct such queries.

Audit Trail Isolation: Audit entries record event_type (BALLOT_SUBMITTED), resource_id (ballot_reference, not voter_id), and status (success/failure). They never record which candidate was selected. Log entries bypass plaintext choice values entirely, using only structural information like "Ballot submitted to constituency: Chennai_South, timestamp: 2024-11-06T10:30:45Z".

14

4.2 Encryption Implementation

Encryption Algorithm: The system uses AES-256-GCM (Advanced Encryption Standard with 256-bit keys in Galois/Counter Mode). GCM mode provides authenticated encryption (AEAD), meaning it detects any tampering with ciphertext and rejects forged votes during decryption. The authentication tag (16 bytes) ensures integrity without separate HMAC computation.

Encryption Key Management: Encryption keys are never stored in application code or configuration files. They reside in AWS Secrets Manager with audit logging of all access. Keys are rotated monthly with versions tracked (key-2024-11-01, key-2024-12-01, etc). Old key versions are retained for 1 year enabling decryption of old ballots if recounting is needed. All key material remains encrypted at rest even in Secrets Manager.

Frontend Encryption: The critical insight is that encryption happens on the frontend before transmission. The backend generates an encryption key using a secure random generator and sends it to the frontend only after eligibility verification. The frontend encrypts the voter's choice (candidate_id and timestamp) using the Web Crypto API's SubtleCrypto interface. The plaintext choice never reaches the backend. After encryption, the key is cleared from frontend memory to prevent accidental transmission.

Backend Decryption: During ballot submission, the backend decrypts the choice only to verify it represents a valid candidate in the voter's constituency. Once verified, the backend stores only the encrypted bytes, never storing or logging the decrypted choice. This ensures even an attacker with database access cannot link voter identity to candidate selection without also obtaining the encryption key (stored separately in Secrets Manager).

15

4.3 Authentication and Authorization

Authentication Mechanism: Voters authenticate using OTP (One-Time Passwords) rather than traditional passwords. This avoids storing passwords, which create security risks if the database is breached. The flow: voter enters phone number, backend sends OTP via SMS (mock SMS for testing), voter enters OTP, backend verifies OTP is correct, not expired (10-minute window), and not previously used. Upon successful verification, the backend issues a JWT token valid for 24 hours. Subsequent requests include the JWT token in the Authorization header.

JWT Token Structure: Tokens use HS256 algorithm (HMAC-SHA256) with a 32-byte secret. The payload includes voter_id, role, election_id, and expiry. The signature ensures tokens cannot be forged or modified. Tokens expire after 24 hours forcing re-authentication. Critical operations also verify token freshness by checking the issuedAt claim.

Role-Based Access Control (RBAC): The system defines five roles with distinct capabilities: Voter (vote only), Officer (review remote polling requests), Admin (election management, user admin), Auditor (read audit trail), System (internal operations). Authorization middleware checks every incoming request, verifying the JWT contains the required role for the operation. A voter cannot access officer endpoints even with a valid token.

Resource-Level Authorization: Beyond role-based checks, the system implements resource-level authorization. A voter can view only their own profile and ballot. An officer can review only requests from their assigned jurisdiction. An admin can view/modify any election. This prevents a voter from accessing another voter's data even with a valid JWT token.

16

4.3.1 Additional Security Measures

Rate Limiting: OTP requests are limited to 3 per phone number per hour. Failed authentication attempts are limited to 5 per hour per account, triggering temporary lockout. API endpoints implement per-user rate limiting (1000 requests per hour typical) with backoff strategies. DDoS protection at the CDN/WAF level blocks obvious attack patterns.

Input Validation: All user inputs are validated for type, format, and range. Phone numbers must match Indian phone number format. Election IDs must be valid UUIDs. Candidate IDs must exist in the voter's registered constituency. Timestamps must fall within election windows. Invalid inputs are rejected with 400 Bad Request before processing.

CSRF Protection: POST/PUT/DELETE requests require CSRF tokens embedded in forms or included in request headers. The server verifies tokens match the user's session, preventing attacks from malicious websites.

SQL Injection Prevention: Parameterized queries are used exclusively. No raw SQL string concatenation ever occurs. The Prisma ORM automatically parameterizes all queries, preventing SQL injection.

HTTPS/TLS Enforcement: All connections use TLS 1.3 minimum. Certificate pinning may be implemented in mobile applications. Content Security Policy headers restrict where resources can be loaded from. Security headers (HSTS, X-Frame-Options, X-Content-Type-Options) prevent common attacks.

  "nonce": "base64-encoded-nonce"

POST /api/ballots/submit

Submits an encrypted vote. The backend verifies the ballot, decrypts to validate the choice, stores only the encrypted bytes, and returns an opaque ballot reference.

Request:

{
  "ballot_id": "ballot-uuid-123",
  "encrypted_choice": "base64-ciphertext",
  "nonce": "base64-nonce",
  "tag": "base64-auth-tag"
}

Response (201):

{
  "status": "submitted",
  "ballot_reference": "BR-2024-0145673",
  "receipt_timestamp": "2024-11-06T10:30:45Z"
}

Critical Implementation Details:

  • Ballot_id verified to belong to authenticated voter
  • Duplicate vote check: SELECT * FROM ballot_submissions WHERE voter_id = $ AND election_id = $
  • If previous submission found → reject with 409 Conflict
  • Decrypt choice to verify candidate exists in registered constituency
  • Store only encrypted_choice, NOT voter_id (ballot secrecy)
  • Audit trail records submission WITHOUT decrypted choice

CHAPTER 6
IMPLEMENTATION DETAILS

6.1 Backend Implementation

The backend follows a modular structure with service classes encapsulating business logic, middleware components handling cross-cutting concerns, and route handlers mapping HTTP requests to appropriate services.

Service Pattern: Each domain (auth, voter, ballot, remote_polling) has a corresponding service class containing business logic. Services use dependency injection receiving the database connection and other dependencies through constructors. This enables easy testing by injecting mock dependencies.

Error Handling: Errors are caught in middleware, logged with structured format (timestamp, error type, context), and returned to clients with appropriate HTTP status codes. Sensitive errors (like database details) are never exposed to clients. Internal error IDs enable correlating client errors with server logs.

Transaction Management: Critical operations like ballot submission use database transactions ensuring all-or-nothing execution. Transactions verify eligibility, check for duplicates, store the encrypted ballot, update voter status, and record audit entry atomically. If any step fails, all changes roll back.

Logging Strategy: Structured logging uses JSON format with fields: timestamp, level (INFO/WARN/ERROR), service name, request_id (for tracing), user_id (anonymized), event_type, status, and context. Logging never includes plaintext OTPs, passwords, or decrypted ballot choices. Log retention is 2 years active, then 5 years cold storage.

6.1.1 Ballot Generation Logic

The ballot generation process demonstrates the constituency invariant enforcement:

async function generateBallot(voterId, electionId) {
  // Step 1: Fetch voter with registered constituency
  const voter = await db.voters.findUnique({
    where: { id: voterId },
    include: { registered_constituency: true }
  });
  
  if (!voter || voter.status !== 'ELIGIBLE') {
    throw new ForbiddenError('Voter not eligible');
  }
  
  // Step 2: Fetch ALL candidates from REGISTERED constituency
  // NOT from remote polling centre!
  const candidates = await db.candidates.findMany({
    where: {
      constituency_id: voter.registered_constituency_id,
      election_id: electionId
    }
  });
  
  // Step 3: Generate ballot from these candidates
  const ballot = {
    id: generateUUID(),
    voter_id: voterId,
    election_id: electionId,
    constituency_id: voter.registered_constituency_id,
    candidates: candidates,
    status: 'DRAFT',
    created_at: now()
  };
  
  // Step 4: Request encryption key (server-side generated)
  const { key, nonce } = await generateEncryptionKey();
  
  // Step 5: Return to frontend
  return { ballot, encryption_key: key, nonce: nonce };
}

The critical insight: voter.registered_constituency_id is used unconditionally, regardless of remote polling status. The remote polling centre influences WHERE the voter votes (physically), not WHICH ballot they receive (their constituency's candidates).

6.2 Frontend Architecture

The frontend is organized into three portals (Voter, Officer, Admin) each with distinct user interfaces and workflows. Common components handle shared functionality (authentication, navigation, error display).

State Management: Redux stores application state in a normalized shape enabling efficient updates. Slices include: auth (logged-in user, JWT token, expiry), voter (eligibility status, profile), ballot (candidates, encrypted choice, submission status), and ui (theme, notifications). Redux Saga middleware handles side effects like API calls, coordinating complex workflows like the ballot submission sequence.

Component Structure: Components follow Container-Presentational pattern where container components handle logic and connect to Redux, presentational components receive props and render UI. This separation enables reusability and testing.

Form Handling: Formik library manages form state, validation, and submission. Custom validators enforce business rules (phone number format, OTP length, candidate selection). Forms disable submission until all required fields are valid and submitted data passes server validation.

Encryption Implementation: The Encryption Service wraps Web Crypto API providing high-level functions like encryptChoice() abstracting away GCM mode details. The service generates nonces, calls SubtleCrypto.encrypt(), and returns properly encoded ciphertext and auth tag for transmission.

CHAPTER 7
TESTING STRATEGY

7.1 Unit Testing

Unit tests validate individual functions in isolation using Jest testing framework. The test suite covers all critical functions with focus on edge cases and error conditions.

Authentication Tests: Verify OTP generation produces valid 6-digit numbers, OTP expiry correctly rejects expired codes, failed verification increments attempt counter, and rate limiting blocks after 5 failures.

Ballot Tests: Verify ballots generate with candidates from registered constituency (not remote polling centre), encryption operations produce ciphertext and auth tags, and duplicate ballot detection rejects second submissions.

Encryption Tests: Verify AES-256-GCM encryption and decryption roundtrip correctly, authentication tag validation detects tampering, and encryption operations use appropriate random nonces.

Target: 90%+ code coverage with emphasis on critical security paths. Developers run unit tests before commit using pre-commit hooks.

7.2 Integration Testing

Integration tests validate API endpoints end-to-end using Supertest library. Tests start an in-memory database, send HTTP requests, and verify responses.

Happy Path Tests: Complete voting flow from OTP request through ballot submission confirms the system works correctly for normal scenarios. Remote polling flow from request through approval to polling centre verification.

Error Case Tests: Ineligible voters are rejected, duplicate submissions return 409, invalid encryption rejects ballots, rate limiting blocks excessive requests, and authorization fails for wrong roles.

Concurrency Tests: Multiple ballot submissions from same voter are serialized by database constraints, with only one succeeding. Duplicate voting attempts are properly detected despite concurrent requests.

Integration tests run on CI/CD before merging pull requests, failing the build if any test fails.

7.3 Security Testing

Security tests verify that attack attempts are blocked correctly. Examples: attempting to forge JWT tokens returns 401, accessing other voter's ballot returns 403, SQL injection attempts are rejected, and CSRF tokens are required for state-changing operations. Manual security testing by third-party firm occurs before production deployment.

CHAPTER 8
DEPLOYMENT AND OPERATIONS

8.1 Deployment Architecture

Local Development: Docker Compose orchestrates backend, database, and frontend services locally. Developers run `docker-compose up` to start the entire system. Environment files configure database URLs and secrets for development. Database migrations run automatically on startup.

Staging Environment: An AWS environment mirrors production with smaller scale. Pull request builds automatically deploy to staging for testing. Smoke tests verify basic functionality. Performance tests measure latency. Security scans check for known vulnerabilities.

Production Deployment: A blue-green deployment strategy runs two identical production environments. The active (blue) environment handles traffic while new code deploys to the inactive (green) environment. After verification, traffic switches to green. If issues occur, traffic switches back to blue.

Auto Scaling: An AWS Auto Scaling Group maintains 3-10 instances based on CPU utilization. When average CPU exceeds 70%, additional instances launch. When it drops below 30%, instances terminate. This ensures responsive performance during election peaks.

Database Replication: The primary PostgreSQL database runs in one availability zone with an automated standby replica in another. If the primary fails, DNS switches to the replica with < 2 second failover time. Backups run hourly with 30-day retention.

8.2 Monitoring and Maintenance

Application Metrics: CloudWatch collects metrics on ballot submission rate, average ballot generation latency, authentication success rate, and error rates by type. Dashboards display these metrics in real-time. Alerts trigger if error rate exceeds 1% or latency p95 exceeds 2 seconds.

Database Metrics: Database latency, connection pool usage, replication lag, and query performance metrics are monitored. Query logs capture slow queries (> 1 second) for optimization. Connection pool exhaustion triggers alerts.

Security Monitoring: Failed authentication attempts, rate limit hits, CSRF failures, and suspicious API patterns trigger alerts. Duplicate vote detection (> 1 per minute) immediately alerts on-call security engineer. Audit trail modifications (attempted deletes/updates) trigger critical alerts.

Incident Response: On-call engineers respond to alerts within 5 minutes. For critical incidents (duplicate votes, encryption failures), the election status changes to HALTED and stakeholders are notified. Investigation procedures follow the incident response playbook documented in Section 8.3.

CHAPTER 9
CONCLUSIONS AND FUTURE WORK

9.1 Project Achievements

This project successfully demonstrates a production-ready remote polling system addressing a genuine social need: enabling geographic mobility without compromising election integrity. The implementation showcases professional software engineering practices across all layers.

Technical Achievements: The system implements the constituency invariant at schema level, making violations structurally impossible. Ballot secrecy is maintained through careful data model design rather than application-level best practices alone. Encryption is implemented with authenticated encryption (AES-256-GCM) providing both confidentiality and integrity. Duplicate vote prevention uses database constraints elegantly rather than distributed locks. Audit trails are immutable and comprehensive. The architecture scales to city-size elections (~500,000 voters) with proper indexing and query optimization.

Security Achievements: The system implements defense in depth with multiple security layers. Authentication uses OTP without password storage. Authorization is role-based and resource-level. Encryption keys are managed separately from encrypted data. Rate limiting prevents brute force attacks. Input validation prevents injection attacks. Audit trails enable investigation of incidents.

Academic Contribution: This project serves as a case study in applying cryptography, database design, and security principles to a sensitive domain. It demonstrates that security and usability need not be opposing forces when designed together from the start.

31

9.2 Lessons Learned

Schema-Level Constraints Matter: Implementing business rules (constituency invariant, duplicate vote prevention) at the database schema level through foreign keys, unique constraints, and check constraints is more reliable than relying on application code. A compromised or buggy application still cannot violate schema constraints.

Front-end Encryption Simplifies Backend: Encrypting voter choices on the frontend before transmission ensures the backend never sees plaintext. This dramatically simplifies the backend's security requirements—it handles only encrypted bytes, never decrypts for storage or logging.

Immutable Audit Trails Provide Accountability: An append-only audit trail that cannot be deleted provides accountability and enables post-election investigation. Even if an attacker compromises the application, they cannot hide their actions from the audit trail.

Opaque References Prevent Information Leakage: Using randomly-generated opaque references (ballot_reference) rather than encoding information prevents accidental information leakage. A reference like "BR-2024-0145673" reveals nothing about the voter or choice.
